# 第 40 轮（2026-11-12）：空闲体检、无人值守流程、界面与文档 —— 两批实施

> 这一轮先量"程序空着的时候在干什么"，再沿六条用户旅程找"出了事没人知道"的缺口，最后看界面和文档。
> 价值排序照旧：漏一集致命、多下一份不是问题、提醒宁可漏报不误报、拿不准就交给人。
>
> **流程**：
> 1. **审计**：性能（后台管线与页面数据函数）、流程（无人值守）、生产实况（库副本与截图），以及 UI 四路、R39 两路回看、测试、文档、安全共九路。每条发现再过一道独立核实（专找"原提案会漏集 / 会自动做错"的地方），多数条目的改法在核实时被收窄或改了方向，实施一律照核实后的改法。
> 2. **注释清理**：先清掉全仓过期的变更史叙述，184 处 / 34 个文件，校验脚本确认代码 token 一个没变。两批实施都以清理后的树为基线。
> 3. **第一批（W1）**：10 个工作包，各自"实现 → 对抗审查 → 修正 → 复审"，两个高风险包（待识别自动转追番、后台缺集自动补）双审，再合入集成树。
> 4. **第二批（W2）**：UI、R39 回看、测试、文档、安全的结论，按文件所有权分 9 个包，以第一批合入后的树为基线。
>
> **验证**：每个包跑自己的必跑文件加两个守卫文件（单一定义、跨 await 登记），全绿；每条新行为都做过变异验证（把改动撤掉对应用例必须红），记录在各包的 NOTES。集成树合入后跑过整套（W2 合入后 2489 passed，约 90 秒）。
>
> **生产数据**：只用了生产库的只读副本和截图；判据没在副本上回放过的（两套集号横幅）不合入。

## 二、逐组落地（细节见代码注释与各包 NOTES）

### 2.1 第一批（W1，已合入集成树）
- **perf-anime**：采集轮末三处不再把只增不减的 sent / skipped 整表拉进 Python（先按触发行或列投影预筛，再取整行）；断更巡检只给"安静超过阈值"的番取分集统计；放行下载期间每交付一条就刷一次"采集在动"（慢取种不再被误报成『采集停摆』）；终集 [END] 豁免断更。
- **perf-engine-main**：补记内容路径的扫描只取三列；启动末尾 `gc.collect(); gc.freeze()`。
- **notify-channel**：`{msg}` 占位符；推送通道连续失败与后台协程退出上横幅。
- **push-texts**：上面那三条推送文案。锁源兜底的放行集合一个没变（用例逐项比对）。
- **keyword-blocked**：`keyword_blocked_episodes`，三个出口（缺集推送、详情页横幅、仪表盘桶）。下载判据一行没动。
- **unmatched-retry**：`_auto_promote` 两处共用；后台重试命中只对自动源建的番（`confirm_reason == "unmatched"`）升追番，且库里不能有另一条番绑着同一个 bgm；次数用完后新集号再给一次机会。
- **log-noise**：日志三项。
- **first-run-upgrade**：首次打开采集的确认框；升级前备份（只对本地 SQLite、本进程只备一次、失败只告警不拦升级）。README 加了『装好之后的 5 步』。
- **digest**：每日摘要（数字全部取自仪表盘同一批函数，不引入新判据；没送到有自己的退避，不连累别的推送）。
- **autofill-gaps**：后台缺集自动补。复审后又补了一轮：只认目标组本身（精确相等）、锁了源而锁定组还没发到最后一集的整部不补、采集暂停时不探 qB、开播前余量封顶到一季长度。完整闸见 DECISIONS 第 40 轮 E-59 复议。

## 三、量到的数字

**空闲**（真实进程、全新库、无浏览器）：启动到首页可访问 1.3 s，RSS 126 MB，空闲 60 秒耗 CPU 0.03 s（0.05%），6 个线程。各后台线反复跑（采集 ×15、仪表盘 ×300、巡检 ×20…）RSS 稳定在约 106 MB，没有随轮次增长的内存。看守、剧场版、重识别、备份、屏蔽列表的心跳空转 0~1 条 SQL。

**随历史行数线性增长的几处**（合成库 110 番 / 3192 条；括号内是 5 倍规模）：

| 场景 | 改前 | 改后 | 节拍 |
|---|---|---|---|
| 采集一轮 `poll_once` | 254.5 ms（534.0） | 215.3 ms（313.6） | 每 20 分钟 |
| 其中轮末事件循环同步阻塞 | 61.6 ms（341.3） | 22.0 ms（101.9） | 同上 |
| 修正版退旧版 `_retire_old_versions`（100 条已下完的 v2） | 32.1 ms / 101 条 SQL | 3.95 ms / 1 条 SQL | 同上 |
| 断更巡检 `sweep_idle` | 10.1 ms（59.9） | 2.2 ms（7.9） | 每 3 小时 |
| 补记内容路径 `fill_content_paths`（500 / 2000 条） | 8.77 / 24.2 ms | 2.79 / 5.66 ms | qB 同步 |
| 全代 GC 一次 | 23.8 ms | 0.3~0.5 ms | 随机落在数据函数里；仪表盘最坏 50.0 → 29.5 ms（未在真进程复核） |

1 倍库上采集一轮的 73% 花在取回与解析 feed（6 组 185 ms，其中 feedparser 约 135 ms；在线程里、不随库增长），不动。

**流量**：feed / HTML 放开 gzip（E-61），四个真 feed 实测 identity 78~95 KB 对 gzip 10~14 KB，每天约 37 MB → 5 MB。

**每日摘要的成本**：20 条 SQL、37 ms（5 倍 217 ms），一天一次。**锁源兜底点名闸**：详情页每部锁源落后的番多约 1 ms（40 部 41.5 ms）。

**首次安装的量级**：今天实拉 ANi feed 75 条、53 部、合计 30.5 GiB —— 开始使用日空着就打开采集，第一轮就是这么多。

**测试套件**：全套约 55~61 秒（第一批合入前 72 个文件、1867 条），其中约 9 秒是真等待（本地 HTTP 服务关停轮询、`asyncio.timeout`、子进程建库）；最慢的单条 1.87 秒。

**安全（第二批要修的）**：重定向中间跳的包体由 httpx 自己解压、四道闸一道都不经过，线上 1 MB → 内存 2 GB；屏蔽列表对第三方 .gz 无上限解压，线上 261 KB → 峰值 1.5 GB；r39 的 `_EPV_TAG_RE` 对一条 512 字符的畸形标题回溯 21 秒（每一轮采集都卡）；Mikan 季度页正则 400 KB 畸形块 31 秒；bgm 简介行尾空白正则 4 万个空格 9.2 秒。

## 四、不做的（含理由）

| 项 | 为什么不做 |
|---|---|
| 两套集号并存的横幅 + 一键锁定源（U1-1） | 判据要先在生产库只读副本上回放、零误报才合入（同类判据记过四次失败）；本轮拿不到副本，顺延，原型留在工作目录 |
| 『不属于本季』整部番按宽判据一键批量（R39A-1 原提案 ③） | 进 DECISIONS E-80 待拍板，推荐不做 |
| 同 URL 复用 feed 解析结果 | 省 44 ms/轮但在线程里（约 3 秒/天），解析结果常驻 282~346 KB/个 |
| qB 同步内层（8 条 SQL / 3 ms）、仪表盘 overview（23 ms / 30 秒 / 可见标签页） | 按 E-53 的尺子不动；overview 要逐行看发布时间判占槽行，GROUP BY 下推不了 |
| 条件 GET（304） | gzip 之后只剩约 3 MB/天可省，且会和"入库失败不推进 seen"打架 |
| alembic 懒加载 | 省 10 MB 但要自己判 head |
| 连接复用、SQLite synchronous | 每轮 4 次握手；稳态每轮只提交 1 次 |
| 给 `_recheck_where` 加索引、合并两表 torrents/info | qB 一天也只 9~14 秒，而这段每个分支都是踩过的坑 |
| nyaa RSS 翻页回放 | 实测不支持（p=1/2/14 逐字节相同） |
| 停滞满 N 天自动换源、失败行自动重试 | 推翻 E-3 / E-19；磁盘满时会变重试风暴 |
| 待确认即时推送 | 会刷屏，由每日摘要承载 |
| 断档记录自动过期 / 自动点『知道了』 | 等于放开 E-74 的断档闸 |
| 异盘备份 `BACKUP_EXTRA_DIR` | 宿主机层有备份手段，且备份里有密钥 |
| 后台协程退出时推送 | 规格不新增推送事件；横幅已经点名 |
| 仪表盘『缺集』弹窗加"全部自动补齐" | 不在第一批规格内 |
| 测试提速（SSRF 服务关停轮询、预检用例拷库） | 60 秒里省 9 秒不值得动守卫；拷库还多一层对 SQLite 旁文件的依赖 |
| DECISIONS 历史小节标题、"18 条"、E-67 原文 | 存档原文不改；只改了顶部总览这份会误导人的索引 |
| R39B-5、R39B-7 | 前者已知已拍板，后者核实时反驳成立 |

## 五、要你拍板的

**进了 DECISIONS 第 40 轮那张表的**：
- **E-59 复议**：后台缺集自动补已按严格闸落地、**默认开（2 天）**，要不要默认开由你定。
- **E-80**：『不属于本季』要不要给整部番一个按宽判据的一键批量，推荐不做。
- **E-67 补记**：设置页先写明了『绑定看着不对跟着待识别积压这个勾走』；E-67 拍 A 时删掉那句。

**实施中留下的小取舍**（默认都取了保守方向，你不说就维持）：
1. 被『终集完结标记』豁免断更的番不记 `idle_notified_at`（与"播完且集齐"那道既有豁免同性质）：日后终集那行被排除或改集号，可能报一条陈旧的断更。
2. 推送通道横幅的门槛 5 与推送熔断共用一个代码常量，要不要进设置。
3. 版本关键词挡住提醒：同步豁免比的是发布时间而不是入库时间；推送里的天数写"N 天以上"（N=设置值）而不是每集的真实天数；它跟着『锁定源落后』的天数开关走，设置页那个标签要不要改名。
4. 同一 bgm 被另一条番占着时不升追番，这道闸只在后台重试这一刻生效；挪进 `_auto_promote` 会改新种子进来时的既有行为。
5. 整轮中途异常或某源卡住时，日志缺"停在哪个源"的线索；建议另做一小项（health 记当前源名，停摆文案带上）。
6. 升级前备份要不要单独限份数（现在与日常备份分开、各留『保留份数』份）。
7. 每日摘要：RSS 断档要不要每天提到点『知道了』为止；剧场版的失败数要不要并进来；时钟在同一天内回拨时不再多发一条。
8. 缺集自动补：某集唯一一条被你排除后不替你补别的版本；锁了源的番大多不自动补（交给锁源兜底）；补不回来的番每天重搜一次、没有逐步退避；源组的标题过滤不作用于后台补缺。

**仍在 DECISIONS 里等你定的旧项**：E-58、E-60、E-62 ~ E-71、E-72（待确认）、E-75、E-76、E-78、E-79、E-31 复议。

## 六、部署须知

- **没有新迁移**：这一轮不加列，所以部署后第一次启动不会触发"升级前自动备份"；它从下一次真有迁移时起作用。
- **新设置项**：`ANIME_GAP_AUTOFILL_DAYS`（默认 2）、`NOTIFY_DIGEST_HOURS`（默认 24）、`NOTIFY_DIGEST_AT`（默认 9）、运行时键 `NOTIFY_DIGEST_LAST`。老库启动时按默认值补上；新事件 `digest` 自动并进已勾的事件。
- **缺集自动补默认就开**：只在采集开着、『发送种子到 qB』开着且 qB 连得上时跑；想先观察就把它设成 0。
- **生产上推送地址仍是空的**：每日摘要、缺集自动补回、通道故障这些推送都要先配好 `NOTIFY_URL`。现在 ntfy 也能配：`https://ntfy.sh/<主题>/publish?message={msg}`。
- **部署脚本**：收尾提示按 `.env` 里实际的 `WEB_HOST` 说话；`.env.example` 加了一行注释掉的 `WEB_HOST`（必须保持注释，deploy.sh 靠"没有这一行"才补 `0.0.0.0`）。
