## 1. 我这轮改坏的（已全部修复）

| id | 问题 | 为什么危险 | 修法 |
|---|---|---|---|
| `BK-01` **critical** | 备份文件名是 `autorss-{scope}-{stamp}.db`，**scope 段排在时间戳前面**，而 `'m'(meta) > 'f'(full)`。按文件名排序时，一份刚做好的 full 备份会排在所有旧 meta 备份**后面**、被自己这次 `prune` 删掉，紧接着 `out.stat()` 抛 `FileNotFoundError` | 自动备份进入「每 10 分钟整库 VACUUM 导出一次再删掉、`BACKUP_LAST` 永不前进」的死循环；UI 显示「共 7 份」却全是旧的仅配置快照。**这个功能是来补『出事就没救』这个空白的，结果它自己就是那个事故** | 排序键改 `mtime`；`prune` 加 `protect=` 参数，刚做好的那份绝不删（最后一道兜底） |
| `BK-02` **critical** | 设置页的恢复指引漏掉 `-wal`/`-shm` | 掉电/OOM 后照做：SQLite 启动时会把**事故现场那份 `-wal`** 重放到刚恢复的库上 —— 拿回的是出事**后**的数据，而 `pragma quick_check` 照样返回 ok。**用户做完了每一步验证、每一步都绿** | 改成四步顺序并写明第 2 步为什么不能省；`db/backup.py` 的模块 docstring 同步 |
| `R4-01` **critical** | 我把 missingFiles 的行塞进 sync 的 rows 一起问 qB，但它们会走「qB 查不到就落定」那套判据 —— 而文件缺失的种子 `qb_progress` 常常正是 1.0，第一个分支就把它清成「已下完」 | UI 从『文件缺失』变『已交付』→ 被归档 → 集去重认定该集已有一份 → 永不补下，而**盘上根本没有文件**，全程不报错。改动前它被 `_inflight_where` 排除，压根进不来 —— **我的「修复」把一个显示问题换成了数据丢失** | 补查行单独成集 `recheck_ids`，在 `d is None` 分支**最前面** `continue`（qB 查不到一条本就报文件缺失的种子，唯一正确结论是维持原状）；也不进 absent 分母 |
| `R4-03` **P1** | 同一批行会被停滞计时抓走：`missingFiles` 只标了 `X` 不带 `W` | 默认 24 小时后从精确的『文件缺失』变成含糊的『⚠️停滞』，既丢诊断，又因 `stalled ∉ TRACKED_STATUSES` 而**永久退出补查** —— 用户在 qB 修好文件也再无出口 | 标记改 `XW`（qB 确实没在推进它），一次覆盖所有停滞判断点 |
| `R3-F1` **P1** | 压缩炸弹封顶按整条 `Content-Encoding` 字符串精确查表。`gzip, identity`（合法多值）查不到就落进「交回 httpx」的回退路径，而**那条路径没有原始字节闸** | 实测峰值回到 **148.3MB** —— 与我在注释里声称「已修掉」的 141.8MB 同量级。小 VPS/NAS 上 OOM kill，日志只留一句「抓取失败」 | 按 token 解析 `get_list("content-encoding")`；回退路径补 `num_bytes_downloaded > cap` 闸 |
| `BK-03` **P1** | `if out.exists(): raise` 是 TOCTOU，且失败时无条件 `unlink(out)` | 后台协程与页面按钮同秒撞车 → **输家把赢家刚做好的那份删掉**，目录里一份不剩，而自动路径照样写下 `BACKUP_LAST` 报成功 | 导出到 `mkstemp` 临时名再 `os.replace`；失败只清自己造的（含 `-journal` 残骸）；加模块级 `threading.Lock` |
| `R4-02` **P1** | 上一轮我用 `kwargs.setdefault("text_color", "dark")` 修 toast 对比度 —— **这是个空操作**。NiceGUI 的 `ARG_MAP` 只把 `close_button`/`multi_line` 转驼峰，其余原样下发，而 Quasar 认的是 `textColor` | 142 处 toast 的对比度仍是 1.9~2.9:1。**「看起来改了、实际什么都没发生」是最难自查的一类** | 改 `textColor`，并加背景守卫（不带 type 时底色是 #323232 深灰，深色前景只有 1.64:1）。补了一条专门防它复发的用例 |

## 2. 既存缺陷（本轮一并修了）

| id | 问题 | 修法 |
|---|---|---|
| `mv-enrich-date-gate` **P0** | 剧场版「重试识别」把**种子上架日**当**首映日**做日期校验。BD/WEB 版普遍在首映后 6~18 个月才发，于是正确的 subject 被判「日期对不上」而排除，转而命中同系列另一部 —— 而下一行就是 `bangumi_id 相同 → _merge_movie`，**直接删掉正主那一行**（连同它已下好的版本），UI 还弹绿色「识别成功 ✓」 | 不传 `release_time`。TV 侧 `services/enrich.py` 早有「基准不可靠就**不设**基准」这条规矩，这里把它用上 |
| `LOG-3` **P1** | Bark/Server酱 的推送密钥在 URL **路径**里，而 httpx 的异常串带完整 URL → 原样落进 `data/autorss.log` 与 `/logs` 页 | 只记状态码与 `netloc`；`services/qbittorrent.py` 的同款（一条异常 4.5KB 还带全部 hash）一并收 |
| `LOG-1` **P2** | httpx 的 INFO 访问日志对每个请求记一行完整 URL，而 `torrents/info` 把上百个 hash 拼进 query —— 单条 4.4KB × 每 30s ≈ **12.7MB/天**，超过日志总保留量 12MB | 把 `httpx`/`httpcore` 压到 WARNING（同款处理见 `db/schema.py` 对 alembic 的静音） |
| `mv-bind-inherits-rejected` **P2** | 手动「绑定 bgm」会继承被合并行的「已忽略」 | 合并后重读并复位。此前 UI 弹绿色「已绑定并识别 ✓」，片却从『列表』和『待识别』同时消失，只能去『已忽略』找 |
| `D8`/`TS-4` **P2** | **httpx 对装不上解码器的编码是静默放行的**：`br`/`zstd`（都不是本项目依赖）会把**压缩字节原样交出来**、不报任何错 → feedparser 拿到二进制垃圾，抛一个与编码毫无关系的解析错误 | 先查 `httpx._decoders.SUPPORTED_DECODERS`，解不开就明确报错 |

| `FR-4` **P2** | `config.py` 的注释承诺 `DOWN_PATH/番剧`，实测落 `/home/26C/<番名>`。`engine.py` 与 `settings.py` 两处说明都对，只有这里错 —— 而它是读代码的人最先看到的地方 | 改成事实 |
