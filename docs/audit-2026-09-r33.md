## 一、E-46：从"枚举写回点"改成"枚举工作单元"

### 问题的形状（为什么 R21→R27 错了四次）

`maintenance_blockers()` 是切库/迁移前的在途预检。它枚举的是"谁跨 await 持着业务库主键"——
而这是一个**开放集**：R21 数出 2 条，R22 数到 4，R23 数到 5，R27 数到 7。
每次都是"这次数全了"，每次都没有。用户的一句话点破了它：

> 切库之前不能先等**全部**完成或者全部停止吗？

问题不在"有东西跑的时候切了"，在"**名单不知道有些东西在跑**"。后台 5 条线都有轮次锁、闸看得见；
真正敞着的是**页面直接调的 core 函数**——用户点『绑定 bgm』，那 120 秒的 await 跑在 NiceGUI 的
请求上下文里，既没有锁、也不是我们 `create_task` 出来的、也不在任何名单上。

### 落地

1. **`engine.in_flight(label)`**：只登记、不串行（锁会让两个不相干的页面操作互相等）。
   页面入口改成 `wrapper → _<name>_inner`，wrapper 用它包住整段；`maintenance_blockers` 多列这一类。
2. **形状守卫**：`tests/test_engine_lifecycle.py::_STRADDLERS` 登记表 + AST 扫描器。
   扫"出 await 之后还开业务库会话"的 async 函数，每一个都必须在表里说清被哪道闸看见
   （`lock:` / `delivering` / `sync_busy` / `in_flight` / `caller:`）。新写一个同形函数不登记 → 红。
3. **有界地等**：两个维护入口先 `await engine.wait_until_quiet(30)`，等不到再走原来的"拒绝并列出理由"。

### 对抗审计当场打穿了第一版扫描器

第一版扫描器只认函数体里**字面的** `get_session(`。对抗审计的探针在 `delete_movie_torrent` 上
**真的把 `deleted` 写进了另一个库**——它的形状是"读主键 → `await qb.delete` → `_set_status(id)`"，
写回经辅助函数，字面上没有 `get_session`。我在第一版 docstring 里写了"已知盲区：session 经辅助函数
打开的看不见，手工列入"——**这句话在逻辑上是空的**：手工列入的前提是知道它在，而它正是不知道的那个。

第二版扫描器改成**跨模块求不动点**：直接调 `get_session` 的算，调本模块已算上的算，
anime/movies 里调 `engine.<已算上>` 的也算；函数体内嵌套 def 若开会话，对它的调用也算
（`engine.relocate` 里的 `_mark_moved` 就是这种）。被 await 的调用本身算，它实参里的调用不算
（实参在 await 前求值）。

第二版比第一版**多扫出 6 个**：

| 函数 | 形状 | 处置 |
|---|---|---|
| `delete_anime_torrent` / `delete_movie_torrent` | 读 → await qb.delete(45s) → `_set_status(id,"deleted")` | 包 in_flight（漏掉的后果：另一个库里随机一行被标 deleted，那一集永远不再补下） |
| `download_pending_for_anime` | 读 id 列表 → await 预检 → 逐个 `download_anime_torrent(id)` | 包 in_flight |
| `relocate_anime` / `relocate_movie` | 一句委托，跨 await 的段在 `engine.relocate` 里 | 包 in_flight；`engine.relocate` 登记为 `caller:` |
| `_discover_loop`（剧场版扫描主体） | 在 `worker._scan_lock` 内 | 登记 `lock:_scan_lock` |

页面驱动的工作单元从 8 个变成 **13 个**——审计验证员说"三四个"，第一版扫出 8，第二版 13。
同一件事第三次被低估，与 `maintenance_blockers` 那四次是同一个形状。

### 对抗审计第二波（完整性视角）又打出四条守卫的洞

审计员先在快照上用探针把四条 P1（就是上表前四行）真的复现了出来——`deleted` 写进另一个库、
`relocate` 把新库『已下』行清成 pending、`download_pending_for_anime` 把**新库里未确认的番**的种子发进了 qB

| 存活的变异 | 洞 | 修法 |
|---|---|---|
| M10：给 `_resolve_anime` 在锁外加一个新调用方，表仍写 `caller:process_item` → 绿 | `caller:` 只查"名字在不在表里"，不核调用图。表里 `enrich_anime ← _resolve_anime` **本来就是假的**（它调的是 `enrich.resolve`） | `_enclosing_callers` 按 AST 收 core/pages/services/main 里每处调用的外层函数，要求恰好 ⊆ 名单；假调用方已删 |

### 第三波（假守卫视角）：闸在自救路上是瞎的

这一条是本轮最重的：`maintenance_blockers()` 读不了业务库时 **`return []`**（R22："别把『切回本地』堵死"）——
而它后面才轮到锁 / `sync_busy` / `in_flight`，**这些是内存信号，与库能不能读无关**，却被一起吞掉。
探针（两个一次性 SQLite）：库读不了 + 『删除单集文件』在途 → 三道预检全拿到 `[]` → 切库放行 →
`deleted` 按旧库主键写进了新库的另一行。触发路径是真实的：MySQL 抖动 → 用户走自救出口 →
此刻恰有一个页面操作停在 qB 的 await 上。

改法：except 里**只跳过 COUNT 那一段**，不 return；交付中的行改按 `_delivering` 登记数。
自救出口在没有在途工作时照样开着；有的话它会说"现在不能"——那正是它该说的。
这改了 R22 的一句行为，理由与代价都写进了函数 docstring；DECISIONS 里记作 E-56（已按 E-46 的授权实施，可退回）。

同一波还打出三条守卫的洞（都修了、M22–M27 复验全红）：
- `test_background_task_handles_are_kept` 只拦裸表达式：`_ = create_task(...)`、存进局部列表都绿 → 现在要求祖先链里是 `background_tasks.extend/append` 或对它的赋值。
- `lock:L` 是纯文字：`process_item → lock:_sweep_lock`（真锁、闸看得见、但它不在里面跑）绿 → 沿调用图往上找，某一层必须有 `async with L`。
- `test_wait_until_quiet_returns_when_the_gate_clears` 对"忽略超时永远等"是**挂死 300 秒**而不是红 → `asyncio.wait_for`。

**审计过程的一个事故**：审计员与我共用了 `scratchpad/mut/` 做变异副本，我 rsync 时可能改了它脚下的文件。
它自己注意到了工作树在变（"18:00:57 再拍活树快照复核"），四条 P1 的结论都在它自己的快照上成立，
所以结论可信；但以后**变异副本按人分目录**（我改用了 `mut2/`）。
