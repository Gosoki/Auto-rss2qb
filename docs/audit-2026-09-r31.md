## 一、R28 修"四位合集包"时把**下界**一起抬高了（P1，潜伏回归）

R28 为修「`- 1156-1170` 被抽成第 1156 集」，把 `_EP_END` 的负向前瞻
从 `\d{1,3}` 换成了 `\d{2,4}`。**上界 3→4 是要修的那件事，下界 1→2 是顺带改的、没人注意。**

于是右端只有一位数的连续集区间不再被前瞻挡住，`-` 重新成了合法的集号收尾锚：

```
[LoliHouse] 某番 - 1-9 [WebRip 1080p]     →  ep=1    batch=False   ← 整包被当成第 1 集
[Nekomoe] Show - 1-6 [1080p]              →  ep=1    batch=False
[组] 某番 - 10-2 [1080p]                   →  ep=10   batch=False
```

走的正是 R28 自己定为 P1 的那条链，只是换了个角落：`_BARE_RANGE_RE` 两侧也要求 ≥2 位、
`1-9` 匹配不上 —— **两道判据同时失效**，`auto_downloadable_ep(1)` 为真，
几十 GB 的合集包被当单集自动下回来，还占死去重键 `(番, 1)`。

补零写法（`- 01-09`）不受影响，所以**真库 2248 条今天 0 条命中** —— 潜伏的回归，不是正在发生的事故。

### 修法：下界本来就不该有

这条前瞻的语义是「连字符后面跟着一个裸数字 ⇒ 这是区间」，位数从来没有下限的道理。
两处一起还原成 `\d{1,4}`（`_EP_END` 的前瞻 + `_BARE_RANGE_RE` 两侧）。
`_BARE_RANGE_RE` 真正需要的那道防线（不把「第二季 - 03」的 `2 - 03` 误判成区间）
由前后两条**环视**兜着，与位数无关 —— 真库 2248 条实测：放开下界后判定变化 **0 条**。

### 守卫的判据也改了：从「上界够大」改成「**区间覆盖**」

上一版结构守卫只断言上界 —— 于是 R28 把 `\d{1,3}` 换成 `\d{2,4}` 时上界从 3 涨到 4，
**守卫满意，下界却悄悄从 1 抬到了 2**。这正是它漏掉这条回归的原因。
现在断言 `lo <= lo_ex and hi >= hi_ex`，两头都要覆盖。
两条变异（分别把两处下界抬回 2）都被结构守卫与行为用例**同时**抓到。

## 二、补下 0 集却报绿：三种成因混成了一种（P2，已修）

一部**待确认**的番里若有 `error` 行，详情页把它标成橙色『失败·可补下』、
tooltip 写着"点右边『下载』或『下载该源』手动重试"；
而 `download_pending_for_anime` 第一行就是 `if not is_subscribed(a): return 0` ——
用户点下去什么都没发生，却收到一句**绿色**的「已触发下载 0 集」。

同一条种子在番剧列表『新入库』里走的是另一条路（先过 `confirmed_anime_ids`）→ 显示红色『失败』。
**两个界面对同一行给出相反结论。** 真库 anime#96『落语朱音』现在正是这个状态。

**根因是记录在案的契约**（第 3 轮 D9）：`download_plan` 只排除 rejected、**不看 confirmed**，
而那条闸在调用方。`tests/test_plan_equivalence.py` 里有一条用例明写「别顺手修它」。
所以这一轮**不动契约**，只修无争议的那一半，并把它记成 **E-54**（附今天的真库证据）。

### 改成：三种 0 分开说

| 情形 | 现在的提示 |
|---|---|
| 闸挡住了 | 「没有触发下载：这部番还在【待确认】…」/「已被【忽略】…」/「已判【完结】且开着停订…」（warning） |
| 有候选但一条没放行 | 「有待补的集，但这一轮一条都没放行 —— 多半是 qB 此刻连不上，去 /logs 看…」（warning） |
| 真的没得下 | 「没有可补下的集（该下的都下过了，或都被锁定源/版本关键词挡住）」（info） |

第三种是**写用例时才发现的**：前一版的 else 分支把 qB 连不上也说成"该下的都下过了" —— 又是一句假话。

### ⚠ 这一组的第一版用例是**假的**，两处都栽了

- 断言写的是 `should_see("待确认")` —— 而详情页对未确认的番**本来就挂着**一个『待确认』徽标，
  不点按钮也能绿。断言必须落在**只有那句提示才有**的字样上。
- `QB_ENABLED` 在夹具里默认 False，此时这些下载按钮是 `disable=True`，
  而 `UserInteraction.click()` **跳过禁用元素** —— 点击根本没发生，两条断言都在空跑。

两条都写进了用例的 docstring。变异：退回"0 集也报绿"→ 4 条红；把三种 0 混成两种 → 1 条红。

## 三、E-30 的显示这一半：剧场版终于全按年（P3，已修）

E-30（已拍板）把 `movie_quarter_of` 钉成恒返回 `<yy>A`，可**消费侧**一直按季度键分组。
后果在真库上很直观：

```
改前：6 个年份被劈成 15 根柱   例：25D 9 / 25C 9 / 25B 5 / 25A 3   ← 全是 2025 年
改后：2026 年 7 部 / 2025 年 26 部 / 2024 年 27 部 / 2023 年 9 部 / 2022 年 1 部
```

而今后新入库的片一律落进 `<yy>A` —— **同一年的新旧片会分在不同组里**。

三个消费点一起改（这是同一个决定，落一处就是第①号形状）：

| 位置 | 改成 |
|---|---|
| `core/movies.overview` | 按四位年聚合；键名 `by_quarter` → **`by_year`**（它装的是年，旧名字会骗人） |
| `/movies` 仪表盘 | 「各季度（剧场版数）」→「各年份（剧场版数）」，柱标签是「2025 年」 |
| `/movies` 列表 | **去掉二级季度小标题** —— 年这一级本来就是分组，二级只剩噪声 |
| 详情页那一栏 | 「季度」→「**年份**」（编辑框本来就叫年份，同一页两个名字指同一个东西最容易读错） |

**顺带让 E-47 变成可选**：存量那 53 条的季母从此不出现在任何界面上，
那条待拍板项现在只剩"库里好看一点"，可以放心不做。已在 `DECISIONS.md` 就地补注。

变异：仪表盘退回按季度分 → 3 条红；二级小标题回来 → 1 条红。

## 四、审计视角一的**排除清单**（时间/时钟/调度：0 条缺陷）

这一节是留档，免得下一轮重挖。全仓 47 处时间用法逐一过了：

- 入库的时间列一律 `datetime.now()` 的**本地 naive**；跨进程比较的（冷却/限流/会话 TTL/负缓存）
  一律 `time.monotonic()`。**两类没有互相串用**，没有拿 monotonic 存库、也没有拿墙钟做限流桶。
  `utcnow` 全仓零命中。
- **方言一致性**：每一条 revision 的 DateTime 列都带 `.with_variant(mysql.DATETIME(fsp=6), 'mysql')`
  （逐条核对过），表全部由 alembic 建（没有裸 `create_all` 路径）—— MySQL 不会退化成 fsp=0 丢微秒。
- 全仓 `func.now` / `CURRENT_TIMESTAMP` / 时间类 `server_default` **零命中**：
  没有任何时间由数据库服务端生成，**不存在"app 时钟 vs DB 服务器时钟"分叉**。

### ⚠ 改名当场打红了一条守卫 —— 而我是跑全量才发现的

把 `overview()` 的键 `by_quarter` 改成 `by_year` 之后，
`test_movie_dashboard_quarter_bars_put_1999_last` 直接 `KeyError`。

**这是守卫在干正事**（它守的是"两位年的季度键做字符串比较时 `'99D' > '26C'`，
1999 年的片会排到当年之上"），所以处理方式是**跟着换键名并把性质写清楚**，
不是"因为改了实现就把守卫删掉"。换成四位年之后按 `-int(y)` 排，那个性质天然成立，
断言也从"首尾两个"收紧成"整个序列 `['2026','2025','1999']`"。

记在这里是因为：我是**写完报告才跑的全量**。顺序应该反过来。
