### E-44 为什么不做（用户提出、核实后成立）

用户问："qB 那边有队列，一口气全发过去等处理会不会更好？"——**对**。
`queuedDL` 在状态表里是一等公民：算在下载中、不算落定（同步循环继续跟）、
停滞计时跳过它（`_QB_NOT_ADVANCING`）、UI 显示「排队下载」。交给 qB 排队比压在我们库里的
`pending` 跟踪得**更好**（pending 是"连 .torrent 都还没取"，queuedDL 是"qB 已拿到、在等"）。
原文"带宽瞬间打满"的理由是错的——qB 的 `max_active_downloads` 就是干这个的。
真正串行的是我们自己的取种循环（`_poll_lock` 内、每条最长 180 秒），但正常取种不到 1 秒。
**唯一前提**：qB 里的"种子排队"要开着。

## E-57（R34 对抗审计提出）：占位记号分不出"崩在交给 qB 之前"还是"之后"

**背景**：E-49 之后崩溃残骸按 `prev_status` 还原（deleted 不再变回自动队列、已归档不再丢 archived_at）。
但 `add_to_qb` 返回 True 与 save_path 回写之间只隔一次 commit —— 那一次 commit 撞上库抖动（E-49 原文列的触发条件之一）时，
**qB 已经收下种子在下了**，行却被还原成 sent+已归档 / stalled / deleted：
- 已归档原态 → progress=1.0 ∉ in-flight、archived_at≠None ∉ 归档轮 → qB 里那份新下载**永远无人跟踪、永不归档**；
- stalled 原态 → 除非配了完成回调，否则永远停在『停滞』；
- deleted 原态 → 文件照常落盘而库里是『已删』。

**旧行为（一律 pending）在这一点上反而自愈**：订阅中的番由 flush 重发 → add 撞已存在 hash 返回 True → sent → 重新纳入跟踪。
新行为不自愈。窗口只有一次 commit，所以是 P3；但它是设计上的缺口，一列记号分不出两种崩法。

| 选项 | 做法 | 代价 | 我的看法 |
|---|---|---|---|
| **A（推荐）** | 清扫复位前先问 qB：`sweep_round` 是 async 的，`sweep_stale_delivering` 复位前 `await qb.torrents_info([hash...])`，qB 里**有**的落 sent + 清 qB 态（与成功段同款）而不是还原 prev；qB 不可达则本轮跳过、下轮再来。启动时的 `reset_downloading` 同理延到第一次 qB 探测之后 | sweep 多一次 qB 查询（只查 downloading 行的 hash，通常 0 条）；启动复位晚几十秒 | 判据是事实（qB 里有没有）而不是记号，两种崩法都答得对 |
| B | 成功段先写一个『已交 qB』记号（如 `prev_status='__qb_added__'`）再写 save_path；复位见到它走 sent 分支 | 记号仍是记号：add 成功与写记号之间还是一次 commit，窗口只是变小 | 治标 |
| C | 接受窗口，只在清扫日志里把"按 prev 还原"的行连 hash 打出来 | 0 | 那就得有人看日志 |

**没有自己做**：A 改的是清扫与启动复位的时序（多一次网络往返、复位延后），是行为口径；按约定交你拍。
