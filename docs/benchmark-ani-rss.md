#### 2.1 ⚠ r14 更正：「集数偏移我们更严谨」这个结论，被真实数据推翻了一半

前几轮是在**空库**上做的对标，这一轮跑在从远端拉下来的真实数据上（1621 条种子），结论要改：

**我们的自动学习几乎没有输入。** `ep_offset` 唯一的信号源是 `- 16(88)` 这种括号双编号标题
（`extract_episode_abs`）。对真库全部 1621 条 `raw_title` 跑一遍，**只有 5 条命中**（0.3%），
而且全部来自同一个组、同一部番。与此同时有 15 部番存在「集号 > 总集数」的行。

**已经造成了实际损失。** `anime#27`「擅长逃跑的殿下 第二季」：ANi 用绝对编号 13–19、
Nix-Raws 用季内编号 1–7，偏移恒为 12（发布日期逐对吻合），
**14 条 sent 全部落在同一个目录** `E:\Anime\AutoRSS\26C\逃げ上手の若君 第二期` —— 7 集各下了两份。

**判据本身不该改。** `_foldable` 的 docstring 明文记载过：按「某源出现过 ep>T 就判定它整源用绝对编号」
取证会被 bgm 少记一集与字幕组中途接手骗过；真库也摆着反例（`#6`/`#60` 的 ep>T 行是**真的正片集**，
一折就撞上已交付的键、被 flush 静默丢掉，而项目明确把「漏集不可逆」排在「多下占盘」之前）。
朴素的 `min(over)-1` 推法在真库 `#25` 上就算错（真 offset=12，推得 13）——这正是 ani-rss 那个 `min-1` 的毛病。

**所以要借鉴的不是它的推断算法，而是它有而我们没有的那个东西：**

> **每订阅（对我们是每番）一个可以手工填的 offset。**

现状是全项目**没有任何 UI 能设 `ep_offset`**——推不出就只能永远推不出。
已有的 `set_torrent_episode` 只能逐条改集号（`#27` 要点 7 次，且下周新集又来一条）。
加一个入口之后，用户在详情页看到「疑似同集不同编号」横幅时填一个数就能一次性收口，
`_refold_absolute_episodes` 会把存量一并回折。这是「人工审批」形态，与本项目
「推不出就不猜、交给人工」的既定取向一致，不改任何自动判据。

> 待拍板项，已记入 `docs/DECISIONS.md`。

| 配置演进 | `@SerializedName(alternate=)` + 加载时用默认对象补齐 + Alist→OpenList 自动改写 | Alembic 双 role，**明确不做 downgrade** | 平 | — | 各有取舍 |
| 数据库 | 无（JSON 全量常驻内存） | 双引擎（配置恒本地 SQLite / 业务可切 MySQL）+ 停摆语义 + 健康看守 | ✅ **我们明显更强** | — | ani-rss 订阅量大时无分页无索引 |
| 主题切换 | 亮/暗/跟随系统 + 强调色 + 自定义 CSS/JS | `ui.dark_mode(True)` 硬编码，配色写死 | 小 | 不做 | 单人自用 |

| MCP / 日历 / Emby Webhook | 全有 | 无 | — | **不做** | 明确超出本项目定位 |
| 测试 | 0 | **473 条 pytest 用例已入库**（约 20 秒、零网络） | ✅ 我们更好 | — | ⚠️ 本行原文「0（有意不入库）」写于第 1 轮，早已被 D-28 推翻 |

### 8 值得借鉴的 Top 5（按性价比）

1. **完结检测 → 自动停订**（`total_episodes` 已在库，判据用现成的 `HAVE_STATUSES` 计数；顺带解锁「完结迁移」，因为 `engine.relocate()` 已经能搬）。
2. **摸鱼检测**（该番最新 `release_time` 距今 > N 天 → 通知）：一条 SQL + 一条通知，是发现「源失效」的唯一自动手段。
3. **通知升级为「事件维度」**：至少加 `失败/停滞/待识别积压/qB 连不上/库停摆` 五个事件，配一个 `NOTIFY_EVENTS` 多选。渠道仍只保留现有的 URL 式（顺手修掉不走代理）。
4. **遗漏检测 + 按空洞补抓**：现在 `backfill_source` 是「按源名搜」，改成「按缺的集号搜」精度更高。
5. **从历史 `raw_title` 自动生成过滤 chip**：扫该源组已有种子标题，提取 `1080p/繁日/简日/HEVC/内嵌…`，在源组编辑框下给一排可点 chip 直接填进 `title_filter`。零后端成本。

### 9 明确不做的

| 项 | 理由 |
|---|---|
| TMDB / 媒体库刮削（nfo/poster/集标题） | 需要连带做文件重命名；用户已有 Emby/tMM 承担这件事 |
| 文件重命名（含 `SxxEyy` 规范化、下载前 rename） | 本项目定位是「把正确的种子送进 qB」，改名后要保证做种/多文件/字幕关联，是另一个产品 |
| 下载器抽象（Transmission/Aria2/OpenList） | 6 个 DB 列名叫 `qb_*`、状态词表是 qB 原生态、104 处引用；抽象需跨方言迁移且本项目无 downgrade |
| 备用 RSS 洗版（自动删旧文件） | 与「不主动删用户已下文件」的产品边界冲突 |
| MCP Server / ICS 日历 / Emby Webhook 回写 bgm | 超出定位 |
| 代理域名白名单 | **我们天然不需要**：qB 客户端不走 `http_client_kwargs`（qB 恒在内网），其余出站（nyaa/mikan/bgm/取种/通知）本就全是外网，全部走代理即可，无需逐域名开关 |
| 多用户 / 权限分级 | 单人自用 |

## §10 r17 复核（2026-08-31）：Top 5 的完成度，以及一处**方向反了**的对标

### Top 5 的现状

| # | 借鉴项 | 状态 |
|---|---|---|
| 1 | 完结检测 → 自动停订 | ✅ 已实现（`sweep_finished` + `ANIME_FINISH_UNSUB`，默认关，理由见 DECISIONS D-02） |
| 2 | 摸鱼检测 | ✅ 已实现（`sweep_idle`，`idle_notified_at` 跨重启去重） |
| 3 | 通知升级为事件维度 | ✅ 已实现，且**已经反超**（见下） |
| 4 | 遗漏检测 + 按空洞补抓 | ❌ **仍未做**。现状：详情页能看出缺集，但不主动提醒、不主动去搜。<br>ani-rss 的做法是「集号 min..max 找空洞，空洞 > 10 视为误判，每集每天提醒一次」。<br>我们比它多一个前提条件：`total_episodes` 已落库，所以空洞可以按 `1..total` 找而不是 `min..max` 找，**不需要那个 >10 的启发式**。<br>但也多一个障碍：本项目有「季内编号 / 绝对编号并存」的问题（`_foldable` / `ep_offset`），空洞判定在有歧义段的番上会误报——所以要么只在 `_foldable` 判定安全的番上跑，要么等 E-29 那类人工入口。 |
| 5 | 从历史 `raw_title` 自动生成过滤 chip | ❌ 仍未做。零后端成本，性价比仍然最高的一条。 |

### 通知这一维：我们已经反超，把它记下来

文档站 `/config/notification` 明确写的是 6 种事件、30+ 模板变量、6 类渠道
（TG / 邮件 / Server酱 / Emby 刷新 / 文件移动 / OpenList 上传），
而**限流、重试、失败处理、多实例，文档里一个字都没有**。

对比我们 r17 之后的状态：

| 维度 | ani-rss | 我们 |
|---|---|---|
| 事件类型 | 6 种 | **9 种**（多出 `qb_down` / `db_down` / `backlog` 三个**带外故障信号**） |
| 渠道 | 6 类 | 1 类（路径式 URL）。**这一项我们仍然差**，但对单人自用够用 |
| 消息模板 | 30+ 变量 | 写死的 f-string。**这一项我们仍然差**，属于「可选」 |
| 状态型事件 | 无此概念 | 边沿触发（只在翻转那一刻发），`_state_now` + 每 kind 独立小桶 |
| 限流 | 文档未提 | 每小时上限 + **按送达记账**（r17）+ 被丢弃条数挂在下一条尾巴上 |
| 发送失败 | 文档未提 | 三态返回（送达 / 拒绝 / 连不上），落库标记与冷却**都等这个返回值** |
| 黑洞地址 | 文档未提 | **连续失败熔断**（r17）。这条不是锦上添花：`notify()` 串在交付主链路上，地址不通时每条要白等满 `NOTIFY_TIMEOUT` |
| 密钥泄漏 | 文档未提 | `_safe_host()` 只记主机名（Bark/Server酱 把密钥放在 URL **路径**里，`urlsplit.netloc` 还含 userinfo） |

**结论**：通知这一维不该再当成"差距"来对标了。它现在是我们的**留档优势**，
下一次有人想"参考 ani-rss 重写通知"时应当看到这一节——那会是倒退。
真正还缺的只有两条：渠道数（低优先）与消息模板变量（中优先）。

### ⚠ 一处此前**方向标反了**的对标：备份

§7 的原文把备份记成「ani-rss 每天 zip 备份保留 7 天；我们完全没有 → 建议做」。
备份这一半我们已经做了（`db/backup.py`，`VACUUM INTO` 而不是 `copy2`，
理由是 WAL 库拷主文件会拿到一份**看着正常、其实缺数据**的库——这一点比 ani-rss 的 zip 更对）。

但 r17 查出来的是**另一半**：

1. **恢复侧从来没有代码**，只有设置页上一段文案。而备份最贵的失败方式恰恰全在恢复那一侧：
   实测用户机器上 5 份备份有 4 份标着绿色「配置+业务」而业务数据是 0，
   照着页面步骤恢复任意一份 = 99 部番静默清零，且 `quick_check` / 启动日志 / `is_data_down` 全是绿的。
   （已修：`verify` 报实际行数、徽标按内容走、恢复步骤改成改名留底。）
2. **ani-rss 有「设置与订阅的导入导出」，我们没有**。这一条原文归在备份行里带过，
   实际上是**独立的一条能力**，而且是我们更需要的：
   本项目的订阅源配置（`SourceGroup`：RSS 地址、字幕组白名单、标题关键词、优先级）
   全部只存在于数据库里，重装/迁移时只能整库搬。
   一个 `导出订阅为 JSON / 从 JSON 导入` 大概 40 行，且**不需要开 revision**。

**新增建议（性价比排在原 Top 5 的 #4 与 #5 之间）**：订阅源的 JSON 导入导出。
