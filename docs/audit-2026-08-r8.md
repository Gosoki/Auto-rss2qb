## 2. 三条改动比它们的描述要大

### D-05：最后的口径是「首跳放行 **+ 同主机同端口的跳转也放行**」

决策原文只写了「首跳放行」。按那个口径实现完，自查时发现它会**误伤一整类正当配置**：
局域网自建服务（ntfy / Bark / 自建 Mikan 镜像）把 http 跳到自己的 https —— 那种跳转
没有把请求送到「别的地方」，而这条守卫要挡的恰恰是**第三方替用户改写了目的地**。
端口一并比：同主机换端口就是换了个服务（`192.168.1.5:9000 → :8080` 很可能正是 qB）。

实现上还有一处值得记：**怎么知道这是第几跳**。httpx 建重定向请求时用
`Request(extensions=request.extensions)`，而 `Request` 里是 `dict(extensions)` —— 浅拷贝，
里面的**可变值是同一个对象**。于是往 extensions 里塞一个 list、在钩子里 append，
计数就顺着整条重定向链传下去，**调用方一行都不用改**。
不用 response 钩子看 `history` 是因为那时请求已经发出去了——对 SSRF 来说太晚。
`tests/test_ssrf.py` 里专门有一条用例盯着这个浅拷贝语义：httpx 若改成深拷贝，
守卫会**静默失效**（不报错、只是不再拦）。

守卫顺带搬进了新的 `core/ssrf.py`：`config.http_client_kwargs` 要用它装默认钩子，
而 config 是最底层、不能反过来 import `core.engine`。装在 config 里的理由是
「新加一处抓取时忘了加」正是本项目反复栽跟头的失效形状。

### D-12：唯一约束差点把「多一行重复」换成「每轮扫描都崩」

`_upsert_movie` 按 `bgm_id` 命中一行之后会**无条件覆写** `mikan_id`。而那个 id
可能正挂在另一行上（一部早期扫进来、当时没识别出 bgm 的旧行）。加约束前必须先「摘」。
不摘就是 IntegrityError，表现为**这部片每一轮扫描都失败**，日志只有一行『处理剧场版失败』。

迁移本身还踩了一个：**`batch_alter_table` 在 SQLite 上按反射到的旧定义重建索引**，
在同一个 batch 里先 drop 再 create unique，收尾时那个非唯一的旧定义会被原样重建回去——
于是索引仍是非唯一，而版本号照写 head。**迁移声称跑过、约束根本不在**。实测复现，已改直接 DROP+CREATE。

存量重复行的处理：保留「有 bgm_id 的、其次 id 最小的」，其余置空 `mikan_id`（**不自动合并**——
合并会删行，而「两行是不是同一部」在那里没有可靠判据）。真库实测：88/340/119/20/228 行全在，重复 0。

### D-24：清掉的两样东西比改名重要

- `config.MIKAN_SUBGROUPS` —— **死配置键**，全仓只有定义处和一条指向它的过时注释，
  真正生效的一直是 `SourceGroup.subgroups`。
- `core/engine._host_is_internal` —— **孤儿函数，且不钉 IP**。留着最危险的地方不是它没被调用，
  而是它**看着像一条安全防线**：下一个人拿它去挡 SSRF，会得到一个存在 TOCTOU 的假守卫。

## 4. 三轮循环的收尾

这三轮（第 6~8 轮）与前五轮最大的不同是**前提被更正了两次**：「没有插件系统」推翻了五轮的架构论证，
「我有 MySQL」把 D-01 从「标实验性」翻成「一等后端」。两次都不是代码问题，是**我把没验证过的假设
当成了事实**——而它们各自主导了好几轮的结论。

至于代码本身，八轮下来最稳定的规律仍然是第 5 轮记下的那条：
**风险最高的代码 = 审查覆盖为零的代码**，也就是每一轮自己刚写下的那些。第 7 轮的
`char_length` 就写在我自己那句「两个方向都要跑，只在一个方向上正确 = 另一个方向一开始就崩」
下面 3 行。本轮把它当成流程来用了：每条改动落地后先问一句「它的兄弟路径在哪」，
D-05 的同主机放行、D-12 的摘 id、D-08 的两半一起做，都是这么找出来的——
**在同一轮里，而不是等下一轮**。
