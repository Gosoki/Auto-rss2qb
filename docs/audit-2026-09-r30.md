## 二、`episode` 的词表漏了一个可达取值（P3，已修）

`db/models.py` 写的是「支持 .5；-1特别篇 -2未知」——**三种**，而实际是**四种**：

| 取值 | 含义 | 能不能自动下 | 算不算"已下 N 集" |
|---|---|---|---|
| `>=1` | 正片（含 .5 插入话） | ✓ | ✓ |
| `0` | 第0話 / 前导集 | ✓ | **✗** |
| `-1` | 特别篇 | ✗ | ✗ |
| `-2` | 未知 / 疑似批量 | ✗ | ✗ |

漏记一个可达取值的后果很具体：下一个人看到库里的 `0` 会当成脏数据，
顺手"修"成 `-2` 或过滤掉，那些前导集就再也下不来。

**顺带把那个刻意的不对称钉住了**：`>= 0`（能不能下）与 `>= 1`（算不算覆盖）
是**两个不同的问题**，不是哪一处写错了 ——
bgm 的 `total_episodes` 从 1 数起，把 0 计进分子会让"已下"比总数还多。
而 `flush` 的 `have_eps` **不设阈值**（按 HAVE 状态整批取），所以 0 也参与集去重、不会重复下。
三处各自正确，但从没写在一起过。守卫两条，变异（把下载阈值"对齐"成 `>=1`）当场变红。

## 三、第 2 项：两个 SQL 的设计，拿执行计划与耗时说话

### 索引与热查询的对账（SQLite，真库 + 放大到 20148 行）

九条主系统热查询，六条走索引、三条全表扫。逐条判：

| 查询 | 计划 | 判断 |
|---|---|---|
| 入库去重（按 hash） | `COVERING INDEX sqlite_autoindex_animetorrent_1` | ✓ |
| 别名定位 `(title, season)` | `INDEX sqlite_autoindex_anime_alias_1` | ✓ |
| 仪表盘"最近入库 50 条" | `COVERING INDEX ix_animetorrent_created_at` | ✓（R21 加的） |
| in-flight | `COVERING INDEX ix_animetorrent_inflight` | ✓（部分索引） |
| flush 的待放行 pending | `INDEX ix_animetorrent_anime_id` | ✓ |
| 集覆盖 | `INDEX ix_animetorrent_anime_id` | ✓ |
| **flush 的 HAVE 全量** | `SCAN` | **✓ 有意，见下** |
| 订阅闸（追番中的番） | `SCAN anime` | ✓（99 行的表） |
| 归档扫描 | `SCAN` | ✓（每 600 秒一次、8ms） |

### 一条**量出来的非收益**（重要，别再重复量）

`flush_ready_downloads` 每轮那条「取所有 HAVE 状态的 (番,集,源)」看着最该加索引：

| | 20148 行 |
|---|---|
| 现状（全表扫） | **14.93 ms** |
| 加 `status` 部分索引 | **16.23 ms**，且 SQLite 仍然选 `SCAN` |

HAVE 行占全表 **31%**（6276/20148）—— 选择率这么低时走索引再回表比顺序扫更贵，
优化器自己就不选。**现状是对的。**

### MySQL 侧的索引缺口：量到了，记成 E-53

`ix_*_inflight` 是 SQLite 的**部分索引**，MySQL 不支持带 `WHERE` 的索引，
而 `status` 在 MySQL 上落成 `TEXT`（`db/dialect._COL_LEN`）——**TEXT 不给长度建不了索引**。
baseline 那条 revision 的注释早就如实记着这个缺口，**只是从没人量过它多贵**。

真 MySQL（`10.0.10.20`，20000 行 / 200 行 in-flight）：

| | EXPLAIN | 耗时 |
|---|---|---|
| 现状 | `Table scan (cost=2046, rows=19894)` | **12.58 ms** |
| `VARCHAR(16)` + `(status,qb_progress)` | `Covering index range scan (cost=43, rows=201)` | **4.34 ms** |

2.9×，但绝对值是"每 30 秒 12.58 ms"＝事件循环的 0.04%，
而代价是 `ALTER TABLE MODIFY` 重写整张表。**建议维持现状**，
库超过 ~10 万行或把 `QB_SYNC_INTERVAL` 调很短时再上 —— 记成 **E-53**。

（实验用的是允许动的 `autorss_audit_tmp`，用完已 `DROP`；
`show databases` 复核过其余库一个没动。）
