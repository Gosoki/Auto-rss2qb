## 1. MySQL：四条缺陷全部修复并在真库上验证

环境：**MySQL 9.7.0**，`sql_mode` 含 `STRICT_TRANS_TABLES`，服务端排序规则 `utf8mb4_0900_ai_ci`
（而我们的库是 `utf8mb4_bin` —— 那是对的，理由见 `db/dialect.py`）。
用户库停在 `b2c9e4f17a03`，**比本版本落后一条 revision**。

> 测试方式：克隆用户库（结构+数据）到 `autorss_audit_tmp` 做破坏性测试。
> MySQL 服务器上**只碰 `test_autorrs` 与 `autorss_audit_tmp` 两个库**，其余一概不动。

| id | 缺陷 | 真库实测 | 修法 |
|---|---|---|---|
| `alias-overflow` | 超长番名的别名查询**永远命中不了**（250 字符的参数不可能等于 VARCHAR(191) 里的值），于是每条种子建一部新番；而插入侧在 STRICT 模式下抛 `DataError` 被吞掉 | **复现：4 条种子 → 4 部重复番、0 条别名**，日志只有一行「番名对照登记失败（不影响入库）」 | 新增 `alias_key()`，**查询侧与插入侧同口径截断**；四处调用点全部统一。修复后实测 4 条种子 → 1 部番、1 条别名 |
| `migrate-overlong-halfdb` | 迁移预检只验列不验数据宽度 → 超长值让迁移炸在中途，而此时目标库**已被清空** | 复现并验证修复：预检拦下，**目标库未被改动** | 预检增加数据宽度扫描（`_overlong_values`），在清空之前跑 |
| `mysql-ddl-no-retry` | 一条 revision 里的多个 ALTER 在 MySQL 上不在同一事务（DDL 隐式提交），版本号最后才写 → 中途断掉后重跑撞 1060 → 被标 fatal，而 fatal **只能人工解除** | **复现：`1060 Duplicate column name`**，每次重启都是同一个死循环 | 两条 revision 的 `add_column` 全改为幂等（先 `inspect` 查列）。修复后从「半应用」状态一次升上来 |
| `migrate-hot-source-db` | 迁移在线程里跑而后台采集仍在写源库 | — | 第 3 轮已加 `_poll_lock` + `_scan_lock` |

**顺带抓到一条我自己刚写的缺陷**：新加的宽度预检用了 `count(*) FILTER (WHERE ...)` ——
那是 SQLite/PG 语法，**MySQL 作源时直接 1064 语法错**。这条预检两个迁移方向都要跑，
只在其中一个方向上正确 = 另一个方向的迁移一开始就崩。改用 `CASE` 后双向都通。
（这正是五轮复盘里那个「广度错误」模式的又一次实例。）

**端到端验证**：整个应用带着用户的 88 部番真实数据跑在 MySQL 上，7 个页面全 200、零异常；
`MySQL → 本地 SQLite` 整库迁移逐表校验一致（88 番 / 119 别名 / 348 种子 / 20 剧场版 / 228 版本）。

## 2. `sources/` 的重复：合并（前提更正后重做的结论）

**前提更正**：这不是「插件契约」问题。`sources/` 就是两个普通模块。
所以不存在「要不要建立注册机制」的架构选择 —— 只剩一个朴素的问题：**这份重复该不该消掉？**

**答案不变，理由更硬**：重复**已经在产生缺陷而不只是成本**。
量化后两个 `_parse` 的差异只有三处（hash 来源、下载地址来源、空名判定与白名单的先后次序），
其余逐字相同；而源层的改动**有 9 次是「同一件事改两遍」**，最近一次只改了一半。

合并后：

- `RssSource` 承载全部共用逻辑；`NyaaSource` / `MikanSource` 各只剩 `site` / `TZ` / `_hash_of` / `_url_of`。
- `_SITE_TZ` 那张字典**删掉了** —— 它是全项目唯一一处「新增源时漏改**不会报错**、只是发布时间整天错」的地方，现在时区是源自己的类属性。
- 硬分派从 **4 处降到 1 处**（`worker` / `pages` / `anime` 补齐 / `engine` 时区 → 全部查 `SOURCES` 表），
  且剩下那一处（nyaa 的 feed 要拼 URL）漏改会立刻报错，不是静默失效。
- 顺带修好两处不对称：mikan 缺的 `feed.bozo` 告警、两个源空名判定顺序不同。

**测试抓到一个真问题**：异常兜底里 `entry.get(...)` 在畸形条目上自己会抛，
异常逃出 `_parse` → 逃出 `fetch` → **掀翻整轮采集**。而这个 `except` 存在的全部意义就是「一条坏条目不该连累其余」。
