## 零、纠正：我在 E-53 里写了一句假话

R30 我在 `DECISIONS.md` 的 E-53 里写着：

> 对照 SQLite 侧同样 20148 行：部分索引让同一条查询走 `COVERING INDEX ix_animetorrent_inflight`。

**这句是错的。** 我当时是拿**手写的字面量 SQL** 量的，而生产走 SQLAlchemy ——
它把 `status` 列表发成绑定参数 `?`，SQLite 无法静态证明查询蕴含 partial index 的谓词，
**计划恒为 `SCAN`**。也就是说 SQLite 侧那两个索引当时**一次都没用上**，纯写放大。

更难堪的是：`core/engine._inflight_where` 的 docstring **本来就写着这件事**
（"别以为 ix_*_inflight 那个 partial index 在起作用……"），
我写 E-53 时没读它，凭自己的量法下了相反的结论。

### 顺手把它修好了（因为当年拒绝的理由已经不成立）

那段 docstring 当年的结论是"有意保持现状：内联能快 40 倍，
却要在 SQL 里拼字符串、给后人留一个看着像注入的写法，不值当"。
**这个理由今天不成立**：`bindparam(..., literal_execute=True)` 是 SQLAlchemy 的一等 API，
由它自己在执行期内联，**没有任何字符串拼接**。

逐项实测（20148 行的真库副本，四种写法只差绑定方式）：

| 写法 | 计划 |
|---|---|
| ① status/progress 全字面量 | `SEARCH … USING COVERING INDEX` |
| ② 再加 `coalesce NOT IN`，仍全字面量 | `SEARCH … USING INDEX` ← NOT IN 那项无辜 |
| ③ **只把 status 换成绑定参数** | `SCAN` ← 元凶就是它 |
| ④ 全绑定参数（改之前的生产写法） | `SCAN` |

耗时（in-flight 为 0 的常态）：**6.270 ms → 0.008 ms**。
这正是那个索引存在的理由 —— baseline 写着"常态『无在下』时不必全表扫两表才能确认为空"。

`_recheck_where` 用不上同一招：它要求 `progress >= 1 或已落定`，
与 partial index 的谓词 `progress < 1.0` 互斥，内联了也选不中。

E-53 已就地更正，并重排成"只关于 MySQL"（那一半结论不变：`status` 是 `TEXT`、建不了索引）。

## 一、`services/enrich` 的 6 处出站绕过四道闸：255 KB 的响应让内存涨 540 MB（P2）

`services/fetch` 有四道闸（请求 identity / 线上原始字节封顶 /
`decompressobj(max_length=)` 增量解压 / 多重编码拒收），而 `services/enrich` 的 6 处
第三方出站是裸的 `client.get/post` + `.text`/`.json()` —— 一条都没生效。

**独立复现**（本地桩服务器，gzip 压缩比 1029:1）：

```
压缩后 260935 字节，解压后 268435456 字节
  fetch.get_text  → 被拦下：TooLarge（解压后超过 16777216 字节上限），峰值 RSS +0 MB
  裸 client.get   → 拿回 268435456 字符，          峰值 RSS +540 MB
```

而 `_mikan_bridge` 就串在采集主链路上（`worker.poll_once → process_item → _resolve_anime`），
`MIKAN_BASE` / `BGM_API` 又都是设置页可改的第三方地址。
这个进程同时是 Web UI、qB 同步、交付协程与看守协程 —— 被 OOM 杀掉就是全没。

**对照更刺眼**：`sources/mikan.fetch_detail` 抓的是**同一台主机的同一个端点**，
走 `fetch.get_text` 就当场被 16 MB 上限拦下。同一件事在两个模块里两种待遇。

### 修法

- `services/fetch` 新增 `request_capped(client, method, url, ...)` → `(status_code, 封顶后的字节)`。
  为什么要新形态：这 6 处都要**自己看 status_code**（429/5xx 要退款、404 要静默），
  用不了会 `raise_for_status()` 的 `get_bytes`；而 bgm 的搜索接口是 **POST**。
- `services/enrich` 新增 `_capped()` 作为**唯一出口**，6 处全部改走它。
- **`TooLarge` 的归一只做这一处**：它不是 `httpx.HTTPError`，而本模块每个调用点接的都是
  `except httpx.HTTPError` —— 让它逃出去就把"尽力而为、拿不到返回 None"的契约变成崩溃。
  在 5 个调用点各写一遍 `except (httpx.HTTPError, fetch.TooLarge)` 正是第①号形状的温床。
  归一成 `httpx.DecodingError`：它是 `HTTPError`（接得住），
  又**不在** `_retryable` 的重试元组里（压缩炸弹重试 3 次没有意义）。

守卫两条：行为面（给 `_search_one` 喂真炸弹，断言走"没问成"那条路且退款）
+ 结构面（AST 扫 `services/enrich` 里不许再有裸 `client.get/post`）。变异同时打红两条。

## 二、Mikan 季度页解析的二次方回溯：37 KB 页面冻事件循环 2.57 秒（P2）

`_ROW_LABEL_RE = id="data-row-\d+"[^>]*>\s*(.*?)\s*</div>` 带 `re.S`：
块里没有 `</div>` 时，**每一个** `id="data-row-` 起点都要让 `.*?` 一路扫到块尾才判失败，
再退回下一个起点重来 —— O(起点数 × 块长度)。实测：

```
起点  2000 / 37 KB  →   2566.7 ms
起点  8000          →  24358.5 ms
```

页面大小仍在 `fetch.get_text` 的 16 MB 上限之内，两道现有的闸都不覆盖这种形状；
而 `_parse_movie_bucket` 是**同步函数、跑在事件循环上**。

### 我先试了个"显然的"修法，实测**没用**

把 `(.*?)` 收窄成 `([^<]*?)`：外层每个起点仍要重试一遍，
8000 起点 **24.4 秒 → 38.7 秒（反而更慢）**；而且它会让
`<div id="data-row-5"><span>剧场版</span></div>` 从"取到"变成"取不到" ——
**性能没修好，行为倒悄悄变了**。

### 真正的修法：正则只找起点，收尾交给 `str.find`

```python
m = _ROW_START_RE.search(blk)        # id="data-row-\d+"[^>]*>
end = blk.find("</div>", m.end())
return html.unescape(blk[m.end():end]).strip()
```

两步都是线性，且捕获内容与旧写法**逐字相同**（包括内层标签那种）。实测：

| 起点数 | 改前 | 改后 |
|---|---|---|
| 2000 | 2566.7 ms | **0.14 ms** |
| 8000 | 24358.5 ms | 0.30 ms |
| 40000 | （分钟级） | 2.81 ms |

守卫钉两件事：**行为逐字不变**（六种形状逐个对，含内层标签那种）
+ **相对倍数**（起点数 ×4，耗时不该 ×10 以上；硬毫秒预算在满负载全量跑里会假红，R26 栽过）。

### ① `_EP_TAIL` 的左分隔符比抽取侧窄（P3，成立）

抽取侧 `_EP_PATTERNS[0]` 的左分隔符是「前一个字符不是数字」，
剥离侧 `_EP_TAIL` 却要求「前面必须是空白」。于是 `[组] 某番剧-05 [1080p]`（连字符前无空格）
集号抽得出来、**番名洗不掉** → `alias_key` 变成 `某番剧-05`，每一集一个身份键。

与 R29 §五之① 修的 `第11.5话` / `Episode 07` 是**同一个缺陷类** ——
当时对齐了 `_EP_MARK` 的两条，漏了 `_EP_PATTERNS` 的**第 1 条（也是最常用的一条）**。

**证伪者独立验了修法是安全的**：把 `\s` 换成 `(?<!\d)` 之后，真库 2248 条只变 1 条，
且变化方向是**变干净**；带连字符的真番名（`Re-Main` / `86-Eighty Six-` /
`Vivy -Fluorite Eyes Song-` / `藤本树 17-26`）全部不受影响。

它同时纠正了原发现的三处夸大，值得照抄：
- 行号差 13（读的是 R31 那批改动落盘前的文件）；
- 「bgm 搜索词也带集号」只对一半 —— `candidate_names` 脏，
  但 `search_query_names` 干净（它多过了一遍 `_EP_LEFT_RE`），所以『补齐该源』不受影响；
- 「每一集各建一部番」是**最坏情形**：现配 6 个源组都被 Mikan 收录，
  `_mikan_bridge` 用 `info_hash` 精确拿 bgm_id、**完全不看名字**，
  所以多半只是每集多一条垃圾 `AnimeAlias`；桥不通时才退化成原描述那样。
- 真库 2248 条今天 **0 条命中**（6 个源组全写成 `' - 05'`）—— 潜伏，不是正在发生。

**顺带**：`tests/test_parse.py` 里 R28 那条守卫的 `forms` 列表**没有"无空格"这一族**，
所以它对这个缺陷是绿的。补两条样例才守得住。

### ② `engine.delivering()` 生产零调用，而**登记那一侧根本没有守卫**（P3，成立）

`delivering()` 这个上下文管理器（`add` 与 `discard` 在同一个 `with` 作用域里）
只被用例用来"模拟一条在途交付"，**生产两条交付路径各自手抄了一份**、
且把 add 与 discard 拆到了两个函数里。

**我独立复现了它最要紧的那半句**（scratchpad 副本，仓库只读）：

```
变异【登记】那一侧的字面量 "AnimeTorrent" → "AnimeTorrentX"   →  0 条失败   ← 假守卫
变异【注销】那一侧的字面量                                     →  1 条失败
```

R29 §三 重写这块守卫时只把 `discard` 钉到了 `finally` 体上，**登记那一侧从没被钉过**。
键写错的后果不轻：`is_delivering()` 对一条**正在交付**的行返回 False →
`sweep_stale_delivering()` 会把它从 `downloading` 打回 `pending`（同一集下第二份），
而 `maintenance_blockers()` 会说"可以切库" —— 正是 R21/R24 建这道闸要防的那件事。
