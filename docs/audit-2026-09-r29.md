## 一、R27 那道『数据本身的判据』是逐表判的，而真库的 `movietorrent` 正是它看不见的那种表（P1）

R28 §一之二 给那条**改数据**的一次性迁移加了一道数据判据，立论写的是
「实时态跟踪在这个**业务库**上跑过没有」，实现却写在 `for model_cls` **循环体内**逐表判。

一张表只要从来没有一行被 qB 同步过，逐表写法对它就恒不成立。真库快照实测：

| 表 | 总行 | `qb_synced_at` 非空 |
|---|---|---|
| `animetorrent` | 1679 | **527** |
| `movietorrent` | **569** | **0** |

剧场版是逐版本人工点下的，很多库里根本没交付过 —— 于是切库之后，
剧场版那张表里正在下的版本会被整表写成 `qb_progress=1.0`，
掉出 `_inflight_where`、进不了补查名单、而 `sent ∈ HAVE_STATUSES` 让去重认定已到手。
**R27 自己定为 P1 的那件事，换一张表原样重现。**

修法：把探测提到循环外，两张表任一命中就整体跳过 —— 口径与立论一致。
守卫补的那条用例**只在 MovieTorrent 那一侧留在下的行**：两张表都放的话，逐表写法也能过，用例就白写了。
变异（退回逐表判）当场变红。

## 二、R27 §二 那条修复只落到一个文件，而守卫也只读那一个文件（P2）

`init_business_state` 有**三个**调用点。R27 修的是设置页那一处，
而 `core/worker.run_db_watch` 的恢复边沿仍是**裸的同步调用**：

```python
if was_down and not now_down:
    init_business_state(reset_leftovers=_startup_reset_pending)   # 事件循环上
```

同一行的 `probe_data_engine` 早就 `await asyncio.to_thread(...)` 了，
顶栏『立即重连』那处也上了线程 —— 只有这一条是裸的。
而它跑在「MySQL 刚回来、可能立刻又抖回去」那一刻：`pool_pre_ping` 重连 5 秒、
慢查询 15 秒才切断，事件循环整段冻住，**而且它是无人值守的**
（另外两处是用户点了按钮在等）。

**守卫为什么没报**：R27 那条判据只 `read_text("pages/settings.py")`。
约束的作用域比验证的小 —— 本项目的第②种形状，这一轮又中一次。

修法：改成 `await asyncio.to_thread(...)`；守卫的文件名改成一张**清单**
（`pages/settings.py` + `pages/layout.py` + `core/worker.py`），
并把"上了线程"的判据从只认 `io_bound` 扩到也认 `asyncio.to_thread`。
变异（恢复边沿退回裸调用）变红。

## 三、一条**真的假守卫**：`discard` 没有被绑在 `finally` 上（P2）

`test_both_delivery_paths_register_and_unregister` 的 docstring 明说要守的是
「注销放在**外层包装的 finally** 里」，而四条断言是：

```
"discard" in dump(outer) ✓   "_delivering" in dump(outer) ✓
[带 finalbody 的 Try] 非空 ✓  "_delivering" in dump(inner) ✓
```

**没有任何一条把 discard 与 finally 体绑在一起。** 实测变异：

```python
try:
    _r = await _inner(...)
    discard(...)          # 搬到成功路径
    return _r
finally:
    pass
```

四条断言逐条仍然成立，**全量 1206 一条红都没有**（我自己复现过一遍）。
而变异之后异常路径不再注销：交付回写撞上 `OperationalError` 时那一行永远留在
`_delivering` 里 —— `sweep_stale_delivering()` 因 `is_delivering()` 为真永远跳过它
（行永久停在 `downloading`、∈`HAVE_STATUSES`、集去重认定已有一份），
`maintenance_blockers()` 又永远数到它 —— 切库/迁移被**永久**拒死。
正是 R25 §一③ 那条 P1 原样重现。

修法两条一起上：
- 静态判据落到**同一个节点**上：`any("discard" in dump(n) for t in tries for n in t.finalbody)`；
- 再补一条**行为**用例：monkeypatch 内层使其抛异常，断言 `_delivering` 空了、
  且 `sweep_stale_delivering()` 真的把那一行复位成 pending。
  静态判据能被"换个写法"绕过，行为用例不能。

两条路径（番剧/剧场版）的同款变异都变红。

## 四、R27 新加的 `_archive_lock` 在**生产驱动路径**上零覆盖（P3）

R27 把归档抽成 `archive_round()`（`async with _archive_lock:`），
理由写着「不是为了好看，是为了能测」。可当时只测了"**直接调** `archive_round()` 时锁被持住"，
**没测生产驱动者会不会走它**：把 `_maybe_archive` 里的 `await archive_round()`
换回 `await engine.archive_old_completed()`，全量一条红都没有（实测）。

巡检那一侧有同款驱动者级用例（`test_the_sweep_loop_actually_clears_delivery_wreckage`），
两侧的验证覆盖不对称。

补一条对称的：把 `archive_old_completed` 打成一个**在函数内部问一次在途闸**的桩，
起 `run_qb_sync` 一轮，断言闸里出现『归档』。变异（驱动者绕过 `archive_round`）变红。

## 五、剩下两条已确认发现（前一轮列为"留给下一轮"）

### ① `第11.5话` / `Episode 07`：集号认得出来，番名却洗不掉（P3）

`_EP_MARK` 的两条与 `_EP_PATTERNS` 的对应条不同宽：少了 `(?:\.\d+)?`、只认 `EP` 不认 `Episode`。
实测：

```
[组] 某番 第11.5话 [1080p]     → name='某番第11.5话'    ep=11.5
[组] Show Episode 07 [1080p]  → name='ShowEpisode07'  ep=7
```

违反 `_EP_MARK` 上方注释自己立的规矩。后果不是"名字难看"：`alias_key` 就是番的身份键 ——
每个小数集号各建一部垃圾番，正片那部收不到这一集；搜索词同样脏
（`_SEARCH_STRIP_PATTERNS` 复用同一份 `_EP_MARK`），bgm 搜不到、永久停在『待识别』。

修法：两条与抽取侧对齐。**真库 2218 条标题逐条比对（含 `candidate_names`），不一致 0 条。**
新增守卫钉的是**行为**而不是正则字面：拿一组覆盖各条写法的样例串跑一遍，
凡是抽得出集号的，番名里就不许再残留集号。两条变异全红。

### ② 备份里带着 `DB_BACKEND` 与 MySQL 连接参数，而恢复流程只字未提（P2）

备份是对本地文件整个 `VACUUM INTO`，`setting` 表原样进快照 —— **`DB_BACKEND` 与 `DB_MYSQL_*` 都在里面**。
业务库在 MySQL 时，恢复一份切库**之前**做的备份 → 重启 → `apply_configured_backend()`
读到 `DB_BACKEND=sqlite`：系统静默跑在**另一份数据集**上，页面显示切换前的旧番剧，
后台采集/交付往本地 SQLite 写，MySQL 上的真数据既看不见也不再更新，全程零告警。
这正是 `db/__init__.py` 的 `_data_down` 注释判定为「比直接停摆危险得多」的那种静默回退。

**更糟的是那个绿徽标**：`has_data` 只数**本地文件里**的业务表行数，
而切到 MySQL 并不会删掉本地那套旧表 —— 于是 MySQL 用户的**每一份**备份都显示"配置+业务"，
恰恰把人往那份旧备份上引。第 4 步的验证方法（"打开首页确认番剧数目对"）也验不出来。

修法：`_peek` 顺手把 `DB_BACKEND` / `DB_MYSQL_HOST` / `DB_MYSQL_NAME` 读出来，
`list_backups` 带出去，页面每一行多一个『业务库指向』徽标 ——
与当前不一致时降级成**橙色**。恢复步骤的第 0 步改成"看清楚**两个**徽标"。

## 六、这一轮又抓到一条**依赖机器状态**的守卫

给备份行加徽标时漏了一句 `import db`（本模块用的是 `from db import backup, ...`，
没有 `db` 这个名字）。`tests/test_pages_render.py` 确实红了 —— **但只是因为我这台机器上恰好有 6 份真备份**。

`_backup_panel` 里那个 `for d in items:` 只在 `backups/` 真有文件时才跑；
在 scratchpad 的干净副本上（`data/` 被排除），`list_backups()` 返回空列表，
**整段行渲染一次都不执行**，两条守卫（`test_no_undefined_names_anywhere` 与渲染用例）**都是绿的**。
换一台干净机器或 CI，就是"全绿地把 NameError 发出去"。

补一条不依赖机器状态的：把 `list_backups` 打成桩、造两行（本地 / MySQL 各一），
断言行真的被构建出来。变异（去掉那句 import）变红。

**另外**，写这条用例时我第一版断言的是完整文件名，红在了 `current_layout` 的**文本截断**上
（`autorss-full-2026010...`）——不是缺陷。断言已改到不被截断的徽标文案上。

## 七之二、把 r27 报告里一处**说过头的话**改回来

对抗验证给 R27 §零 那条（键名迁移）提了三处收紧，我逐条核实后**都成立**，已就地改进 r27 的文档：

| 我原来的说法 | 实测 |
|---|---|
| 读起来像"你的数据现在就有危险" | **重跑必然，但今天重启损坏为 0**：真库 `sent 且 progress<1` 是 **0 行**，且 `QB_ENABLED=false` —— 关 qB 时交付走 `settle_inflight_off` 当场写 `sent+1.0`，**产不出在下的行**。风险是潜伏的：重新开 qB 之后、有种子在下时首次重启（或切库）才会吃到 |
| 「归档倒计时留在武装状态、下载当场中断」 | 放大了。`archive_old_completed` 头一行 `if days <= 0 or not QB_ENABLED or not QB_SYNC_STATUS: return 0`；即便开着，还要求那条种子 **120 天后仍未下完** |
| 「全程零告警」 | 略过头。`qb_summary` 会把这行**两边都算**，仪表盘上留一个永不下降、速度冻结在 0 的『下载中 N』 |

**主后果与 P1 定级不变。** 但"把风险说得比实际严重"和"把它说轻"一样是错的 ——
读报告的人要据此决定什么时候重启。
