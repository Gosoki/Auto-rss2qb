## 一、按你的决定实施

### 列表显示：去掉「已完结」，改成 `已下/可下`

- 按【集号】数，不按种子条数——同一集常有好几个源各一份，按条数数出来的比值没有意义。
- 分子 = HAVE 状态（sent/downloading/stalled）的不同正集号；分母 = 库里见过的不同正集号。
- 三色：相等=灰、`已下<可下`=橙（有集号没到手）、`可下>bgm 总集数`=红（集号本身就不对）。
- 真库上立刻有用：`#92/#93/#94 = 0/5`、`#8 = 8/16`；标红 5 部，正是 #6/#8/#27/#60 那几个已知案例
  加上 #67（`0/11` 而 bgm 记 10 集）。
- **只保留「已停订」一个徽标**：那不是状态描述而是【行为变化】（这部番不再自动下新集）——
  去掉它就回到 D-03 修之前那个"用户只觉得它好久没更新"的坑。

### E-32（你让我判断）：不加列

把 `sweep_finished` 改成【先通知、后落标记】，同样拿到"通知丢了下一轮会重来"这个性质，
不用开 revision。关键在于 `False` 有两种含义必须分开：

| 情形 | 处理 |
|---|---|
| 推送正常 | 通知成功 → 落 `finished_at` |
| 推送坏着 | 通知失败 → **不落标记** → 下一轮 sweep 重新判、重新通知（自愈） |
| 没订阅 / 没配 URL | `notify_event` 恒 False，但那不是"丢了"是"本来就不发" → **照常落标记** |
| 首轮回填 | 本来就不推送 → 照常落标记 |

少了第三行就会变成：没配通知的用户 `finished_at` 永远写不进去、停订永远不生效。
代价（有意接受）：推送坏着那段时间 `ANIME_FINISH_UNSUB` 对这几部暂时不生效，它们继续下新集——
安全方向（多下几集 ≪ 停订一部还在更新的番）。

## 三、我在这一轮里犯的三个错

### ① 差点用 `git checkout` 删掉整轮工作

做 E-21 的变异验证时写了 `git checkout core/engine.py core/manual.py` 想回退变异——
工作区里那两个文件装着这一整轮的改动，那条命令会把它们全丢掉。
**被权限分类器拦下了**。之后一律用 `cp` 出的备份文件回退。

### ② 同一个坑踩了三次：守卫做字符串匹配，而我自己的注释里就含那个词

三次分别在 `pages/settings.py` 的两条守卫和 `qb_done` 那条上——
解释"为什么不用 X"的那句话把用例判红。现在这类守卫一律查 AST 的真实调用节点。

### ③ 把 E-18 错误地搬到了剧场版侧

我发现 `_merge_movie` 在自动路径（扫描）上也会删行，就照 E-18 的形状改了。**是错的，已回退。**
两者形状不同：

- 番剧侧 E-18 防的是"自动识别把 X **绑错**到 bgm B，然后删掉本来正确地占着 B 的 Y"——
  错在【绑定】那一步，删掉的是一部完全不同的番。
- `_upsert_movie` 的 keeper 是**按 bgm_id 查出来的**，守卫命中时两行本来就声称同一个 subject，
  合并是构造上正确的；而且 `_merge_movie` 先把种子搬到 keeper 再删行，盘上文件不受影响。

真正危险的是**摘 mikan_id** 那条路（R17 修的），那里两行只是先后引用过同一个 mikan_id，
"同一部片"从没被证明过。两者的差别已经写进代码注释与用例 docstring。
