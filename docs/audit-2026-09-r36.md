## 三、落地的改动

### A. 逻辑 / 潜在问题

- **交付中的占位行，旁人一律让路**（logic-1 / logic-3）：`settle_inflight_off` 与 `_recheck_where` 各补 `status != "downloading"`；
  `maintenance_blockers` 在途交付改数 `_delivering` 登记、不再读业务库（R33 用例改成"一次 get_session 都没调"）。
- **启动清扫的异常不再杀死巡检协程**（latent-1）+ **七条后台协程任何一条意外退出都留一行 ERROR**（`worker.log_task_exit`）。
- **wrb 推送记账绑定送达**（notify-1）：三分支 + 失败时剪掉已离场成员；真路径守卫。
- **完结闩的旧键认领提到两道早退之前**（logic-2）：一个从没有过命中的库也会认领 `_FINISH_BACKFILL_DONE`，
  不会等"下一个恰好有命中的业务库"去认（那个库会被当成回填过、首批完结通知静默）。
- **`_merge_movie` 补上 `_merge_anime` 那条季度护栏**（logic-7）：keeper 没落盘、loser 有文件 → 用 loser 的季度，新版本不与旧文件散在两个年份目录。
- **仪表盘对退避重试中的待下行说『重试中』**（logic-5）：以前说『备用项』（同集已有更优版本），与详情页对同一行的说法相反；`recent_anime_rows` 投影 `retry_at`。
- **搬迁确认框区分两种来路**（logic-10）：目录真的变了 → "移到新目录"；目录没变、盘上有 N 集落在别处（上次没搬成） → "搬回来"。`rows_in_wrong_dir` 算完就丢的那个 `stale` 终于被用上。
- **`maintenance_blockers` 遍历的两个内存容器先快照**（latent-3）：它常在 `run.io_bound` 的线程里跑，事件循环那头正在增删登记。
- **保存设置只在真的改了 `NOTIFY_*` 时才清通知冷却**（notify-8）：以前改个轮询间隔就把 failed/stalled 的 6 小时冷却整个清掉，下一轮把同一批告警原样再推一遍；同文件的『发送测试通知』早就为此专门避开了。

### B. 前端速度

- 两个 30 秒定时器 `immediate=False`（frontend-1）：页面加载那一刻不再把实时区逐字重建第二遍（仪表盘 34 条 SQL / 157 ms）。
- `_parse_date` 加 `lru_cache`（frontend-2）：`suspect_wrong_binding` 34 → 12 ms（真库 100 番）；缓存边界写死 + 守卫。
- `db/transfer.count_rows` 14 次往返 → 2 次（frontend-5）：表名一次取齐、7 条 COUNT 合成一条标量子查询；返回形状一字不变（迁移比对靠它）。

### C. 请求量

- 同一轮采集里同 URL 的 feed 只抓一次（load-1）：真库两对源组同 URL，每天少 144 次第三方请求 / 12 MB；缓存字节不缓存解析结果，过滤各组各跑；按"后面还有没有源要用"逐个释放。
- gzip（load-2）是拍板项 E-61：每天 37.4 MB → 5.2 MB，但要放开 R32 的闸①，不替用户定。
- qB 同步的两处重复请求（load-4/5）量了数字没动：今天 QB_ENABLED=false 收益为 0，热路径等真开起来再看。

### D. 推送

- 番剧交付通知改用 bgm 纠正后的展示名 + 季号（notify-6）：以前是 `种子行的 anime_title[集号]`，同一部番三种写法、跨季同集号分不清（真库 54 组）。
- 剧场版交付通知带版本身份（notify-7）：`文件夹（来源 · 标题片段）`，以前同一部片 53 个版本推出来一模一样。
- 桶分账 / failed·stalled 静音 / 缺的事件键 / `backlog` 一键三义 → E-63 / E-64 / E-66 / E-67。

### E. 体验

- 8 个长操作按钮的 loading 真的亮了（ux-1）；『立刻刷新』有转圈（ux-2）；仪表盘有『上次采集』与『N 个源抓取失败』（ux-5）。
- 『待确认』『已忽略』补『全部展开 / 全部收起』条（ux-6；默认展开策略 → E-70）。
- 顶栏『跳转到』的触发行可聚焦（ux-7）：`:focus-within` 那条兜底以前是死的（容器里没有任何可聚焦元素），键盘与 ≥1024px 的触屏都打不开。
- 剧场版侧面向用户一律叫『版本』（ux-8，Q9=B 早已定）：术语表注释、『版本状态』『版本数』『暂无正在下载的版本』『最近 50 个版本』。
- 『已完成』『下载中』补 tooltip（ux-9）；`kpi_cards` 那个从未用过的"标签色"第 5 元素连同描述它的注释删掉（ux-11；组标题 → E-71）。

### F. 注释说实话

`unknown_episode_rows`（episode<0 不是 ==-2）、`auto_off_reasons`（判序 rejected → not confirmed → finished，且 pending_breakdown 没有『已忽略』档）、
`qb_summary`（排除的是 missingFiles + 7 个过渡态，不是"唯一例外"）、`MovieTorrent.retry_count/retry_at`（剧场版没有自动重试，两列恒 0/None）、
`anime_save_path` / `movie_save_path`（下载走的是**当前这一条**种子行，"同口径"只对已识别的番成立 → E-62）、
`loop_error` 的"13 处"改成不写死数字、`maintenance_blockers` 那段 R22/R33 的 COUNT 叙事改成现状。

## 六、这轮学到的

- **配置的镜像不是状态**。『采集开启』『轮询间隔』四枚徽标一枚都不说"实际发生过什么"；一个"每天看一次、只想知道有没有事"的用户，最该被告知的恰恰是唯一告知不到的。
- **同一个不变式的两半要同一口径**（GLOSSARY 第②号形状再现）：rows 那一半在 Python 里过滤了 downloading，补查那一半没有；`settle_inflight_off` 是"旁人让路"漏掉的第 8 处。
- **`(e=None)` 与 `(e)` 一个字符的差别**让 8 个按钮的 loading 死了两轮，而测 `busy_action` 自己的用例对它免疫 —— 又一次"用例测了自己传的参数"。
- **缓存要写死它的层级**：纯函数上安全的 lru_cache，往上挪一层就漏掉真实输入，且现有用例抓不到。
- **对抗核实要按项目自己的尺子定级**：七条 P2 被拉回 P3 不是发现错了，是探查者没用 E-53/E-5/E-49 那把尺。下一轮探查提示词里直接把尺子写进去。
- **"恢复边沿会补做"这类承诺要查触发条件**：那条边沿库一直好着永不触发，真兜底的是长睡后每轮的清扫。
