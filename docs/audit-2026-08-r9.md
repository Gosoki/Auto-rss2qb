## 1. 一句话结论：漏的形状变了

前七轮的病是**广度错误**（该铺的没铺开）。这一轮它还在，而且距离依然荒唐地近：

| 修了的 | 漏了的兄弟 | 距离 |
|---|---|---|
| baseline 的 6 个建表包了幂等闸 | 同函数里两条 partial index | 20 行 |
| `_resolve_inner` 罩了声优小超时 | `_fetch_by_id_inner` 裸调 | 同文件 102 行 |
| D-03 补了 else 那支的解释 | `elif t.retry_at:` 那支 | 同一条 if/elif 链，11 行 |
| `movies._upsert_movie` 加了快照回写 | `anime.enrich_anime` 两条无 relocate 链路 | 同一份 docstring 立的契约 |
| flush 的候选带 `retry_at` 闸 | `download_plan` 两处 | 同文件 |

**但这一轮还长出了一种新病：约束的作用域比验证的作用域大。**
广度错误是「该铺的没铺开」；这类相反——**已经自动铺开了，我只验了一条**：

- `movie.mikan_id` 加唯一索引 → 顺带对**整库迁移**生效 → 源库有重复时，目标库被清空后炸在 movie 表上
- `_RESOLVE_BUDGET=120s` 套在 `fetch_by_id` 外面 → 把 `_fetch_cast` 的 270s 从「慢但成功」翻成「失败」
- `_MAX_CANDIDATE_NAMES=3` → 对所有候选名生效，而且截在繁简孪生之后
- 停订闸 `finished_at IS NULL` → 让详情页那句「X 时之后自动重发」变成一个永不兑现的承诺

以后加任何**收紧型**改动（新约束/新预算/新上限/新过滤条件），要问的不是「我改的这条路径对不对」，
而是**「还有谁在这个约束的作用域里」**。这是一个和广度检查不同的问题。

还有一处位置转移：**覆盖为零的地带从「刚写完的代码」搬到了「存量库的升级路径」**——
五条 P1 里三条只在旧库上出现，而 tests/ 全部用的是新建库 fixture。

## 3. 测试自身的问题（这一节最值得看）

同一个坑、同一个文件、第二次。

## 4. 查实后**不需要改**的

- **D-18 在老库上并不进去**：两名验证者结论相反。我自己判了——`NOTIFY_EVENTS` 与
  `_KNOWN_NOTIFY_EVENTS` 是**同一个 commit（7fb45bf）引入的**，那个危险状态没有任何已发布版本能产生。
  证伪方是对的，不改代码；但那条 `known is None` 分支确实零覆盖，补了用例。
- **`_MAX_CANDIDATE_NAMES` 会不会截错**：三名验证者用**真实 bgm API** 跑了约 2900 条当天在线的真实标题，
  cap=3 与不截断的最终 `bangumi_id` **分歧 0 例**。所以它是文档问题，不是缺陷。
