## 一、P0：维护窗口一开，七个页面全部构建失败

R21 给维护提示块写的是 `tint("orange")` —— 而 `_TOKENS` 里只有
blue/green/red/amber/grey/ink-soft，**没有 orange**：`tint()` 直接 `KeyError`。
而 `_db_down_notice()` 在 `frame()` 的 `try: yield` **之前**执行，那个兜底够不着。

于是用户在设置页点『切到 MySQL』/『切回本地 SQLite』/『迁移数据』的那几十秒里，
**任何一次开页/刷新/导航都是白屏** —— 偏偏那正是他盯着屏幕等结果的时候。

这条分支在 R21 是**零覆盖**的：4 条 maintenance 用例全停在 `db` 这一层，渲染那一层一次没走到。
约束的作用域大于验证的作用域，第②号形状。

修法：`tint("amber")`（表里已有的暖色），图标色也从写死的 oklch 换回 `text_token("amber")`。
补了「维护期间七个页面仍要渲染出来」的行为用例 + 「提示块用的颜色都在 token 表里」的结构守卫。

## 二、在途闸：同一个函数上，第①号形状连中三次

`engine.maintenance_blockers()` 的职责是：维护（切库/迁移）**开始之前**确认没有协程
跨 `await` 持着旧库的整数主键 —— 因为 `db/transfer.py` 保留主键，
**两个库里 id=501 是两条毫不相干的记录**。

| 轮次 | 它列了几条 | 漏了什么 |
|---|---|---|
| R21 | 2 条（交付中的行、qB 同步） | 采集轮、剧场版扫描轮 —— 当时把这两条"留给调用方记得拿锁"，而 `_migrate` 拿了、`_switch_backend` 一把都没拿 |
| R22 | 4 条 | **延迟重识别** —— 它没有任何轮次锁，而 `retry_unmatched` 单轮最多 50 部、每部 `await enrich.resolve()`（预算 120 秒，全项目最长的 await 之一），出 await 后按同一个整数主键写回 |
| R23 | 5 条 | 页面上还有四个同形入口（见 E-46） |

R23 的修法：
- 给重识别加一把 `_enrich_lock`，**锁在 `reenrich_scope` / `retry_unmatched` 这一层**
  （不是两个调用方各拿一次 —— 那正是漏的来源）。
- 判据里逐条列全五条线，并补一条守卫：**仓库里每一把模块级轮次锁都必须被在途闸看见**。
  这条守卫当场就找出了我漏登记的第六把（剧场版侧的 `_dl_lock`，与番剧侧 `_download_lock`
  同一件事、两个名字），逼我把豁免理由写清楚。
- `_migrate` 不再自己拿那两把锁（拿了会被自己判成"采集轮正在跑"，维护永远开不起来）；
  语义从"等它跑完"改成"正忙就拒绝" —— 一轮采集可能几分钟，按钮转几分钟的圈比一句话更糟。

### 顺带修掉的：这道闸差点把唯一的自救出口堵死

`maintenance_blockers()` 要对着 `db.engine` 发两条 COUNT —— 正是那台**连不上的 MySQL**。
而 `switch_data_engine` 的 docstring 明写"切回本地 SQLite"是 fatal/停摆时的**唯一自救出口**。
第一版没接异常：MySQL 一挂，这个 R21 新加的预检就让『切回本地』必然失败（实测弹"切换失败"，
engine 一步都没动）。现在库层异常一律视作"没有在途交付"。

## 三、R21 那条"过渡态无条件补查"在生产里是死代码

R21 修的是 `_sync_qb_status` **内部**，而它唯一的后台调用方 `run_qb_sync` 的内层
`while … and has_inflight()` 挡在前面 —— 触发那条新分支的行恰恰是
`progress=1.0 + qb_state=moving/checkingUP`，**正好让 `has_inflight()` 返回 False**。

R21 那条守卫自己的第一行就是 `assert not engine.has_inflight()` ——
它测的是 `sync_qb_status`，测不到"worker 会不会调它"。**改动的作用域大于验证的作用域。**

修法：`engine.needs_qb_poll()` = `has_inflight()` 或 有停在过渡态等补查的行，
worker 三处把门一起换；新用例**从 `run_qb_sync` 那一层进**（起协程 + kick），不再直接调 sync。

## 四、其余修掉的

| 项 | 问题 |
|---|---|
| **看守协程的假告警**（R22 的修不彻底） | R22 只在 `while` 顶端查了一次维护标记，而 `await asyncio.to_thread(probe)` 是真实挂起点：维护撞进那个窗口照样推假的『数据库停摆』。现在 await 之后再查一次 |
| **`loop_error` 漏了量最大的那个** | R22 收口了外层循环那一圈 13 处，漏了 `poll_once` 里**每条目一次**那个。维护若在采集中途开始，一轮几十到几千条各打一行 ERROR，而 /logs 环形缓冲只有 200 条 —— 一次切库把实时视图整块冲掉。改成整轮早退，只留一行 INFO |
| **脱敏过滤器打断了噪声过滤器** | `_RedactUrls` 无条件把 `record.exc_info` 清成 None，而它挂在 ring 上、**总是第一个跑** → root 上的 `_SuppressDeletedSlot` 判据恒为 None，NiceGUI 断连噪声整个滤不掉 |
| **`role` 闸守卫是假的** | `body = src[src.index("def upgrade("):]` 切到文件末尾，把 `downgrade()` 一起装进去；而两条 revision 的 `downgrade()` 里恰好各有一句 `_role()`。删掉 `upgrade()` 里的闸，守卫仍绿 —— 而漏写的后果是**把业务表建进配置库**。改成 AST 只看 `upgrade` 的真实调用节点 |
| **`PROXY_URL` 是唯一不做保存前校验的网络项** | 填成 `127.0.0.1:7890`（没有协议头，而占位符只写了 "http://…"）→ httpx 在**建 client 那一步**抛 ValueError → 取源/识别/通知/qB **全线断**，日志却指向各自的 URL |
| **完成归档对它的目标用户恒不生效** | `archive_old_completed()` 只在外层循环跑，而内层 while 只要每轮都有一条在真下就永不退出。`QB_ACTIVE_FLOOR_KBPS=0`（设置页写着"0=只要有速度就算"）+ 一条涓流种子就能永久钉住。改成墙钟节流的心跳 |
| **`enrich_movie` 不合并只是把删行推迟了一轮** | R21 去掉了这里的合并，可**删除动作在 `_upsert_movie` 里原样保留**，而那一处的立论是"keeper 是按 bgm_id 查出来的" —— 一旦识别路径把未经证明的 bgm_id 写进去，立论就变成循环论证，下一轮扫描会**全自动**删掉正主。现在撞车时**连绑定都不写** |
| **番剧页（默认首页）的定时器缺停摆闸** | 剧场版页的同名函数早有，注释还写着"番剧页也是这个口径" —— 而番剧页根本没有。MySQL 掉线时首页每 30 秒撞一次库，建连接同步、上界 5 秒，每开一个标签页翻一倍 |
| **绑定被冻结却报绿** | 有已归档版本时 `keep_path` 把片名/目录全冻住（对的），但页面无条件弹『已绑定并识别 ✓』，而紧接着的 relocate 因为路径没变直接 return —— 用户明明是来纠正认错的片名的，绑定报成功、片名还是错的。现在冻结这件事会回报给页面，文案改成黄色警告并给出怎么办 |
| **MySQL 用户的本地库不再升级** | R21 把 data 链从 `init_db()` 摘掉之后，`DB_BACKEND=mysql` 时**没有任何路径**再升本地那份 SQLite。而『本地 → MySQL』恒取它当源，`migrate_data` 按 head 的列读它 → 失败（安全失败，目标未动），而错误提示说的"用本程序打开它跑一次升级"对 MySQL 用户已经**无路可走**。改成在用户明确要读它的那一刻升一次 |
| **两个 revision 的注释描述了不存在的建库路径** | `b7d2e4a91c66` 的注释写着"全新库由 metadata 建出来的就带着它" —— 本项目**只有一条建库路径**，全新库同样是一路 alembic 建过去的。R21 刚为了杀掉这个信念把索引守卫重写过，注释里又把它复活了 |
| **`trim_alias` 的判据与 docstring 说的不是一回事** | docstring 承诺"保留 anime_id 较小的那条"，实现却按**别名行 id** 排，解包出来的 `anime_id` 一次没用到。两条超长别名 + 顺序相反时，番会静默裂成两半，而这是一条**改数据且不可回退**的 revision |

### ⚠️ 一处要如实记下的偏差：真库的 schema 被推进了

三轮里我一直说"真库未被改动"。**终验时发现不成立**：

- `data/autorss.db` 的 `alembic_version_data` 从 `a3c9e1f70b28` 变成了 `b7d2e4a91c66`，
  并且多出了 `ix_animetorrent_created_at`（就是 R21 新开的那条 revision）。
- 你那个实例（PID 144568）从 09-01 18:35 起**没有重启过**（`reload=False`），所以不是它跑的。
  时间戳落在 R22 审计工作流的运行窗口里 —— 是某个审计子进程越过了"只读"这条指令。
- `data/autorss.db.bak-*` 六份备份**只是被打开过**（多出空的 `-wal`/`-shm` 旁文件），
  内容一字未改：版本仍是 `a3c9e1f70b28`、没有新索引、行数与各自的时间戳一致。

**实际影响**：数据没有丢（99 / 1676 / 70 / 569，与线上一致），而这条 revision
本来就会在你下次重启时自动跑；它在这个库的副本上、以及真 MySQL 上都验过，幂等。
线上实例仍在正常采集（`data/autorss.log` 里 00:18 还在入库）。

**唯一要留意的**：库现在停在 `b7d2e4a91c66`，而这条 revision 只存在于**未提交的工作区**。
如果在提交之前把代码回退到旧版本再启动，alembic 会报
`Can't locate revision identified by 'b7d2e4a91c66'` —— 那正是 DECISIONS E-1 里
记录过的那种"两个版本号永久错位"的形状。**提交之后这个风险就消失了。**

真 MySQL（`10.0.10.20/autorss_audit_tmp`）上另跑过：新 revision 的三条路径（全新/存量/幂等），
以及**真数据 2561 行**的整库迁移（整个迁移放在 `db.maintenance()` 窗口里），校验一致。

⚠️ 机器上有用户自己的 autorss 进程在跑（`reload=False`，不受工作区改动影响）。
三轮全程只按精确 PID 关自己起的测试实例，没有用过 `pkill -f`。
