## 二、交付登记：从"两个地方对齐"收敛成一处 `with`

这是 R30 记下的两条 P3 合起来的样子，本质是**同一个缺陷**：

```
inner（锁内）：engine._delivering.add(("AnimeTorrent", int(torrent_id)))   ← 字面量键
wrapper（finally）：engine._delivering.discard(("AnimeTorrent", int(torrent_id)))   ← 又一遍
查询侧：is_delivering(model_cls, tid) → (model_cls.__name__, int(tid))    ← 第三种写法
```

三处靠"字面量恰好等于类名"对齐，**没有任何机制守着**；而 `engine.delivering()`（键在一处生成、
注销由 with 保证）躺在那里生产零调用。写错一个字母的后果不是"查不到"这么轻：
登记进去的键查不到 ⇒ `sweep_stale_delivering` 把**真在途**的行当成残骸复位 ⇒ 集去重当场解除、
同一集被另一个源下第二份到同一目录，而交付协程回来还会把它写回 sent。

改法：两条 wrapper 都改成 `with engine.delivering(Model, tid): return await _inner(...)`，
inner 里那行手写 add 删掉。副作用（有意接受）：登记的起点从"进锁、幂等短路都过了之后"提前到
"函数一进来"，于是被幂等短路挡掉的调用也会短暂登记几微秒 —— `maintenance_blockers` 那一瞬多报一条，
无实际影响。

### 顺带把守卫换成更强的判据

R28 在这条守卫上记过一次假守卫：
`try: _r = await _inner(...); discard(...); return _r / finally: pass` —— 四条断言逐条成立、
全量一条不红，而异常路径从此不注销。R28 的修法是"把 discard 钉在 finally 体上"；
**改用 `with` 之后那个变异从构造上就写不出来**（注销由语言保证），守卫只需要核两件事：
inner 的调用在 with 体内、且 wrapper 的每个 await 都在 with 体内。
另加一条 `test_nobody_hand_writes_a_delivering_key`：core/pages/services/main 里除 engine 自己外，
不许再出现 `_delivering.add/discard`；engine 里那唯一一处的键不许含字符串字面量。

**写这条守卫时当场踩了一次自己记过的坑**：第一版用 `ast.dump(fn)` 全文查 `"AnimeTorrent"`，
而我在同一个 docstring 里正把它当反例写着 —— 守卫被自己的解释判红。判据改成只看 `key = ...`
那个赋值节点的 value。（memory 里"字符串匹配会被自己的注释满足"那条，这次是反向的同一形状。）
