## 二、告警已读归档（用户提的）

用户的原话：「这些找个地方收起来吧，做一个已读的归档，不然越积越多」。

设计跑了一个判官面板：**4 个独立方案 × 4 个视角评审**（20 个 agent、280 万 token）。
四个方案在架构上撞成了同一个（身份+事实两段、id 必须掺 `created_at`），
分歧只在存储与 wrb 的复活判据。评审打穿了几处跨方案的硬伤，最终形态：

| | 定案 | 为什么（都是评审在真库上复现过的） |
|---|---|---|
| 存储 | 业务库新表 `alert_ack` + 一条 revision | 走 meta 的 `scoped_flag` 的话，用户点一次『迁移数据』`data_identity` 就变 ⇒ 数据一行没动而**全部已读复活**。项目里"用户说这个别再显示"的先例（`finish_optout`、`excluded`/`deleted` 终态）也全在业务行上 |
| 身份 | `kind:{id}@{created_at.isoformat()}` | **不用 `timestamp()`**：naive datetime 按本地时区解释（换机器/改时区 → 全复活），且截到整秒会撞（真库 100 部番只占 97 个不同的秒） |
| 指纹 | 全是**原始位**，不含展示串、不含单调增长的计数 | `a_state` 不是单射；`an/mn/bad` 每采一条种子就变 |
| 复活 | 指纹逐字不等即复活，无阈值、无魔数 | 另一个方案用 `max(saved+4, saved*1.5)` 阈值，自己承认是拍的 |
| 列表 | **对话框**，不是就地 `ui.expansion` | `overview_head` 每 30 秒被 timer 重建，展开去点『取消已读』还没点到就合上 —— R27 为完全同构的 bug 付过学费，而现有守卫的名单硬编码四个面板、不含它 |

### 两处只有评审才发现的

**① 已读必须同时作用在推送上。** 三类里 `wrb` 有推送通道（`sweep_alerts`）。只让仪表盘认『知道了』的话，
横幅没了而手机每 6 小时照旧响一次 —— 第①号形状。

**② 而且归档动作本身不能触发推送。** 推送的去重键是 id 集合哈希：归档一条会让集合从 `{6,12,30}`
变成 `{12,30}`，那是个**从没发过的新 key** ⇒ 用户点了『知道了』反而收到一条新推送
（反向：取消已读会撞回刚发过的旧 key 被 6 小时冷却吃掉）。
改成判"有没有**新成员**"——这也把 `_fingerprint` 那段 docstring 的本意（"条数原地兜圈子也要说"）
实现得更准：`{a,b,c} → {a,b} → {a,b,d}` 里的 `d` 照常发。

**③ 那条守卫本身也差点是假的。** `services.notify` 的冷却记在**进程内存**里，照着
"跑两次 sweep、断言第二次没发"去写的话，有缺陷与无缺陷两种实现都不会发（第二次被冷却吃掉），
用例恒绿。所以那两条守卫每次断言前清冷却、断言**发出去的正文**而不是"什么都没发生"、并带正向控制。

**④ `wrong_binding` 有两条判据。** 第二条（`total_episodes==1` 却收到多个正片集号）命中时坏集号恒为空 ——
指纹若只装坏集号，那一整类读过一次就**永远**不会再报。所以指纹装的是"触发集号的全集"。
