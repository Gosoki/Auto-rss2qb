## 0. 又一条 P0，又是上一轮的修复自己引入的

r11 修好了 `【咒术回战】第二季` 的**番名**，却把**搜索词**弄坏了：

```
工作树： anime_title='咒术回战'   candidate_names=['第二季']
HEAD ： anime_title=''          （整条丢弃）
```

而 `search_names` 是 `enrich.resolve` 的**唯一入参**。于是两部不同的「第二季」
（咒术回战 / 葬送的芙莉莲）都拿 `第二季` 去搜 bgm，拿到同一个条目 → 合并成一部番。
两道闸都拦不住：`_name_not_contradicted('第二季', …)` 靠 2-gram，随便一部「…第二季」都过；
`_date_ok` 在集号 ∉[1,30] 或 release_time 缺失时整段失效。
损坏链与 r11 §0 那条一样不可逆，而且 `retry_unmatched` 只捞 `bangumi_id IS NULL`，**绑错的永远不会被重识别**。

**根因是老毛病的新形态**：`_clean_name`（定番名）与 `_clean_for_search`（定搜索词）
是同一件事的两半，r11 只给前者加了解包回退。
**这次把「要不要解包」抽成 `_unwrap_name_block()` 一个函数，两条路径共用**——它们不可能再分家。

**而这条能过关的直接原因**：全仓 `tests/` 里 `item.search_names` **一次都没被断言过**。
已补 8 条走源真实入口的用例（回退后全红）。

## 2. 已修（按价值）

| 问题 | 关键点 |
|---|---|
| **alembic 可被两个线程同时跑** | alembic 的 `EnvironmentContext` 是**进程级模块代理**，重叠时后退出的那个会删掉对方的代理。而本项目真的会并发调它（看守协程每 30 秒的探测、『立即重连』按钮、`run.io_bound` 里的整库迁移），**一把锁都没有**。副本实测 6 次：**4 次留下「版本号=head 而唯一索引没建上」**（`if cur == head: return` 让这一态**永远不会被修复**），**2 次整进程 SIGSEGV**。加锁后 60 线程零异常。锁必须加在 `schema.upgrade` 这一层——根因是进程级代理，不是引擎选谁 |
| **搜索词塌成季名** | 见 §0 |
| **残渣当番名** | `【我推的孩子】Ⅱ` → 番名 `Ⅱ`；`【咒术回战】 完结` → `完结`；`修正版`/`2期` 同族。**讽刺的是本模块早有一份「这不是番名」的词表**，但它只在解包回退里被调用、主路径从不问它——同一个词写在括号里判成标签，写在括号外就成了番名。`_usable_name` 现在会问它 |
| **`2024年10月新番` 挡不住** | 月份分支从行首锚定，年份一加就落空。而这类标题正是上一轮那条 P0 的修法**明确交给** `parse_multibracket` 的，交过去之后它会犯同样的错 |
| **`restore_anime` 没跟上 `dedup_key`** | 它是 `dedup_key` 的**第六条**消费路径，r11 只改了兄弟那条。歧义段上，A 源已下的『13』会把 B 源真正的第 13 集永久挡在外面，而页面弹的是绿色「已恢复到『订阅中』」 |
| **空源库照样清空非空目标** | 用户先切到 MySQL（本地 SQLite 因此一直是空的），过后"为保险"再点一次迁移 → 目标就是他正在用的库，六张表被清空、写入 0 行，而 `verify` 拿 0==0 判"一致"、页面弹绿色成功。**用户唯一可能察觉的时刻反而确认了一切正常**，而 MySQL 后端下备份 scope 恒是 meta，业务数据一条都不在备份里 |
| **设计语言第二层**（上一轮报告 §3） | 抽 `busy_action` 收成一份，接上 11 个按钮（识别/绑定类是 **120 秒的死键**，连点会并发跑好几轮并重复弹搬迁确认框；数据库那五个共用一个键天然互斥）。切库失败不再报绿色。`live_status` 判序对齐 `pending_breakdown`，并区分待确认/已忽略/已完结——此前三种一律显示「待确认」并把用户指去一个**它们根本不在里面**的 tab |
