## 一、按钮：26 种写法 → 18 种角色，25 处调用点字号全部收回全局

这是徽标那个问题的翻版，只是上了一层。查出来的形状一模一样：

- 全站 **71 个按钮**，**26 种 props 组合**，其中相当一部分只是 **token 顺序不同**
  （`flat dense size=sm color=primary` 与 `size=sm flat dense color=primary` 是同一个东西）。
- **25 处调用点自己写死字号**。根因是 Quasar 的 `size=` 渲染成**行内 font-size**，
  档位只有 `xs8 / sm10 / md14 / lg20 / xl24`，而本项目想要的 12px 不在表里——
  于是 23 个按钮统统写成 `size=sm` 再叠一句 `.style("font-size:12px")` 把 10 掰回 12。
- 代价不是难看，是**同一个角色出现两种尺寸**：`pages/anime_detail.py` 里同为
  `flat dense size=sm` 的按钮，一处被掰到 12px、一处 14px，全凭哪个调用点先写。

修法与徽标同一条原则——**尺度由全局定，调用点只选角色**：

```
.q-btn.btn-sm{font-size:12px!important}      # 唯一的尺度开关，写在 _HEAD_BADGE_CSS 旁边
```

`!important` 的理由也同上：要压的是 Quasar 写在元素上的**行内** font-size
（author `!important` 胜过 inline 非 important），以及调用点顺手加的 Tailwind 工具类。

props 归成一套语法 `{形态} {round} {dense} {color} {no-caps}`：

| 形态 | 含义 |
|---|---|
| `unelevated` | 实心无阴影 = **主操作** |
| `outline` | 描边 = **触发器**（点开还有下一层：下拉菜单 / 批量动作） |
| `flat` | 无底色 = **取消与次级** |
| `dense` | 表示**行内**（列表行、元操作行），**不表示"更小"** —— 尺寸只有 `.btn-sm` 一个开关 |
| `no-caps` | 只在标签含拉丁字母时需要（Quasar 默认转大写，中文不受影响） |

### 顺带修掉的两处硬漂移

| 位置 | 问题 |
|---|---|
| `pages/anime_detail.py` 季度弹窗的『保存』 | 全站 14 个主操作里唯一没写 `unelevated` 的一个 —— 它带阴影，别的都不带 |
| `pages/anime.py` 的『重新识别』 | `size=sm` + `.style("font-size:12px")` 叠出全站唯一一个 12px 的**页头**按钮，而它上下都是 14px |

### 守卫

`tests/test_ui_badge_style.py` 新增两条：

- `test_every_button_uses_a_registered_role` —— props 组合必须在角色词表里登记。
  **用白名单而不是"检查有没有 unelevated"这类规则**：角色是语义，规则是形式；
  白名单逼着加新样式的人回答一句"它是什么角色"，规则只会被绕过。
- `test_no_button_sets_its_own_font_size` —— 调用点不许写 `font-size`，
  文字按钮不许用 `size=sm`（那是 10px）。

### 顺带清掉的两处"同一件事写在两处"

- `pages/layout.py` 里徽标那段注释被**整段贴了两遍**，两份的数字还互相矛盾（19/52 与 31/40，
  实际是 71）。合成一份。
- `.q-table .q-badge{font-size:14px}` 是徽标字号的第二处定义，已由全局 `!important` 那条覆盖，删掉。

（全仓扫了一遍"同一文件里重复出现的长注释块"，只有这一处是真的；`db/models.py` 那处是
`AnimeTorrent.status` 与 `MovieTorrent.status` 各一份，属文档化的对称实现。）

## 二、双引擎与 SQL：是不是最优解 —— 拿真库量过再说

### 热查询：没有一条需要加索引

真库 99 番 / 1649 种子，副本上跑 20 次取均值：

| 查询 | 耗时 | 计划 |
|---|---|---|
| 仪表盘·各状态计数 | 0.59 ms | 全表扫 + 临时 B 树分组 |
| flush·候选筛选 | 4.64 ms | 全表扫 + 主键回查 |
| episode_coverage（全库） | 0.75 ms | 全表扫 |
| 番剧列表（按季度） | 0.60 ms | 全表扫 + 临时 B 树排序 |
| 失败/异常页 | 0.21 ms | 全表扫 |
| 详情页·某番全部种子 | 0.02 ms | 走 `ix_animetorrent_anime_id` |
| 别名反查 | 0.01 ms | 走 `ix_anime_alias_title` |

全表扫在这个量级上**比索引快**（1649 行 0.6 ms）。线性外推：10 万条种子 ≈ 36 ms、
100 万条 ≈ 360 ms，而仪表盘 30 秒刷一次。**结论：现在加索引是过早优化**，
真要加也得等到种子表上 10 万行——那对应大约 60 倍于当前的使用量。

### "循环里开 session" 不是 N+1

AST 扫出 3 处（`core/anime.py:2255` 延迟重识别、`core/engine.py:416/444` 完成归档），
逐个看过：**每一圈中间都夹着一次外部 await**（bgm 查询 / qB 删种）。
在 await 上跨着持有 session 才是错的——那是长事务 + 锁争用。每条一开一关是对的写法。

代价量过了：MySQL（10.0.10.20，同机房）每个"开事务→查→提交"往返 **2.43 ms**，
同连接内单查 0.75 ms。归档一轮封顶 `_ARCHIVE_BATCH` 条，DB 开销 ≈ 0.5 秒，
而同一圈里的 qB 删种调用远比这贵。**不构成问题。**

### 两条 alembic 链：E-1 记的那个缺口补上了

7 条 revision **全部**手抄了 role 闸，一条没漏。但 `docs/DECISIONS.md` E-1 说的
"**没有任何机制拦得住漏写**"当时是成立的——现在不成立了：

`tests/test_upgrade_path.py::test_every_revision_gates_on_role` 会在漏写时当场变红
（造了一条无闸脚本验证过）。漏写的后果值得写下来：同一个 revision 在两个引擎上**各跑一次**，
默认布局下两个引擎指着同一个 SQLite 文件所以本地看不出异常；切了 MySQL 之后
meta 引擎指向只有 setting 表的本地库，迁移要么在"表不存在"上炸、要么安静地把业务表建进配置库。

**E-1 本身（要不要收成一条链）仍然待你拍板**，这条守卫只是让"在它定下来之前不要再被咬一次"。

## 四、对抗审计（四视角）第一批结果：4 处已修，全部有真库证据

> 视角三、四（UI / r17 回归）仍在跑。以下每一条我都**自己独立复现过**再动手。

### ① 真库里两部**仍在播**的番被判成了完结 —— 已修

`is_finished` 用 `ambiguous_range(a) is not None` 表达"两套编号并存时 coverage 是假的"。
但 `ambiguous_range` 要求 `a.ep_offset` 非空 —— **这道守卫只在系统已经学到 offset 时才说话**，
而最危险的情形恰恰相反：offset 未知时一条都不折算、不按 (集号,源) 去重，coverage 更假，守卫全程沉默。

真库实证（不是构造的，是 2026-08-31 06:47:08 那一轮 `sweep_finished` 写下的）：

| 番 | 总集数 | 首播 | ep_offset | 手里的集号 |
|---|---|---|---|---|
| #6 超超超超超喜欢你的100个女朋友 第三季 | 12 | 2026-07-05 | None | 1–33 |
| #60 北斗神拳 拳王军杂兵们的挽歌 第二季 | 12 | 2026-07-06 | None | 1–20 |

两部都是 7 月新番、当时只播了 8 周。

**判据选择走了一个弯路，值得记下来**：第一版写的是"coverage 里同时有 >T 和 ≤T 的集号就不判"，
当场被本项目**自己的用例**否掉 —— `test_extra_episodes_beyond_total_are_fine` 记着
"bgm 的总集数少记一集是真实存在的，多出来的集号不该拦"。那条用例是对的，
而"超界几集才算两套编号"只能拍一个阈值。

改用**时间**就不用拍阈值：**一部 12 集的周更番，首播才过 8 周，它就是不可能已经播完。**
全库回扫：挡下的正好就是这两部，其余 57 个候选零影响。
而且 `sweep_finished` 的**撤销**分支会在下一轮把已写上的 `finished_at` 自己清掉 —— 不用人工改库。

已知代价（有意接受）：非周更的番会被推迟判定，最多到"首播 + (T−1) 周"。
这是 `is_finished` 自己 docstring 的方向 —— 晚判几周只是徽标晚出现，
误判会在开了 `ANIME_FINISH_UNSUB` 时**停订一部还在更新的番**。

### ② 上一条的**根因**：旧季正片被下进了本季目录 —— 已修

`_episode_cannot_belong` 的两个条件是 AND：① 集号超出本季总集数，② 发布时间远超本季播出窗口。
docstring 自己写着条件②的道理是"一季播完很久之后不会再有新集"。

**对称的那句话同样成立：一季首播之前不会有本季的集。但这个方向永远走不到** ——
条件① 先把它挡死了：字幕组补发的旧季正片，集号天然落在 `[1, total]` 里（第一季第 3 集就写 03）。
于是"发布时间比所绑季首播早了两年半"这个极强的信号，一次都没有被看过。

真库：anime#6 底下挂着 24 条 `[ANi] 超超超超超喜歡你的 100 個女朋友 - 01..24` —— 标题不带季标记，
全是**第一季**正片，早 134~143 周，且**已经 sent 进了第三季的目录**。它们填满 1..12 这些槽位，
于是 ① 里那个完结误判就发生了。

补上与②对称、且**独立于①**的第三条分支（不看集号）。余量取多少见 DECISIONS **E-34** ——
`total+26` 周零误伤，收紧到 4 周能多抓一部但证据太薄。全库回扫：
`binding_looks_wrong` 命中数 1 → 2（新增的就是 #6，另一部是早已知的 #100），无误伤。

### ③ 搬迁失败一次之后，再没有任何入口能补搬 —— 已修

番剧与剧场版两侧的 `maybe_relocate_*` 都写着 `if new_path == old_path: return`，
而**四个调用点拿到的 `old_path` 也是同一个 `*_save_path(id)` 算出来的**。
这道闸问的是"我这次操作把记录改了没有"，不是"盘上的文件跟当前归档目录对得上没有"。

真相就记在 `AnimeTorrent.save_path` 上。真库一例：anime#96『落语朱音』10 集躺在
`26C\AKANE On My Mind〜饅頭こわい`（旧的错绑名），记录早已改成 `26B\あかね噺`，
而界面上**没有任何地方还会提出搬它**，`engine.relocate` 的提示还会指向一个没有文件的目录。

判据抽成 `core/engine.rows_in_wrong_dir()` 一份，两侧各调（这正是形状①的高发处），
并加了一条广度守卫钉住"两侧必须走同一份"。

### ④ flush 的候选查询：同一函数三条同类查询，优化漏了最大的那条 —— 已修

`flush_ready_downloads` 一轮有三条对 `animetorrent` 的查询，早先只有两条做了列投影，
漏的偏偏是最大的：整行 ORM，且把"这条属不属于订阅中的番"放在 Python 里逐行 `continue`。

真库量化（1649 条种子、59 部订阅中）：SQL 本身 **8.68ms → 3.16ms**，
取回行数 **1092 → 790**（少掉的 302 行属于没在订阅的番，原本白装配一遍再丢掉）。
ORM 整行装配的开销不在这个数里，那部分省得更多 —— 旁边那条注释记着"9700 行时光装配就 150ms"。

### ⑤ 我自己在修的过程中写出了一条形状③的假用例

`test_wrong_finish_flag_gets_revoked_on_the_next_sweep` 返回了一个 int、一个断言都没有。
是 pytest 的 `PytestReturnNotNoneWarning` 把它照出来的，不是我自己发现的。已删除，
真正那条（`test_wrong_finish_flag_is_revoked`，跑真的 `sweep_finished` 并断言标记被撤销）留下。

**本节 4 处修复全部用回退法验证过**：把判据改回旧写法，对应用例立刻变红。
