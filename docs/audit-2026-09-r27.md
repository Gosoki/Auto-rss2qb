## 零、R26 那次改键名是一条 P1 回归，会在你下次重启时触发

R26 把三个"一次性回填"的标记从全局键改成 `<键>@<业务库身份>`（`db.data_identity()`），
**理由是对的**：标记住在 meta 库、判的却是业务库，切库之后两个方向都错。

**但是没有迁移旧键。** 而你这台机器上，meta 里存的全是旧名：

```
_QB_PROGRESS_BACKFILLED = '1'
_idle_backfilled        = '1'
_FINISH_BACKFILL_DONE   = '1'
```

一个带身份的新名都没有。于是升上 R26 的代码之后，**下一次启动**新键读不到，
三条一次性回填全部重跑一遍。其中最重的那条 `backfill_legacy_progress_once`
是**改数据**的迁移：

```python
for t in s.exec(select(model_cls).where(
        model_cls.status == "sent", model_cls.qb_progress < 1.0)):
    t.qb_progress = 1.0
```

`status='sent' 且 qb_progress<1.0` 命中的正是**正在下载**的种子。被写成 1.0 之后
它们永久脱轨、且零告警：掉出 `_inflight_where`（同步循环再也不查它），
`qb_state` 仍是 `downloading`、不在 `_QB_NEEDS_RECHECK` 里（也进不了补查名单），
而 `sent ∈ HAVE_STATUSES` 让集去重认定这一集已到手 —— flush / 补下 / 换源永不再碰。
调用链是无条件的：`main.py` → `worker.init_business_state()` → 本函数。

### ⚠ 这条的暴露面：**重跑是必然的，但你今天重启不会损坏任何数据**

（R29 补，被对抗验证纠正过来的一处 —— 我上面那段容易被读成"你的数据现在就有危险"。）

真库实测：`animetorrent` 的 523 条 sent 行里，`qb_progress<1.0` 的是 **0 行**，
`movietorrent` 一条 sent 都没有。而 `QB_ENABLED='false'` ——
关 qB 时交付走 `settle_inflight_off`，当场写 `sent + 1.0`，**根本产不出"在下"的行**。

所以准确的说法是：
- **重跑必然发生**（新键读不到，这一条已实测复现），
- 但那一刻 WHERE 命中的行数 = 当时正在下载的种子数，**今天是 0**，
- 风险是**潜伏的**：你重新打开 qB 之后、在有种子正在下时首次重启（或切库），才会吃到。

另外两处也一并收紧：① 归档那一节被我放大了 —— `archive_old_completed` 头一行
`if days <= 0 or not config.QB_ENABLED or not config.QB_SYNC_STATUS: return 0`，
`QB_ENABLED=false` 时归档整个不跑；即便开着，"把还在下的种子从 qB 移除"还要求它
**120 天后仍未下完**，是小概率尾部，不是主后果。
② "全程零告警"略过头 —— `qb_summary` 会把这行**两边都算**（按 `qb_state='downloading'`
计进『下载中』、按 `qb_progress>=1` 计进『已完成』），仪表盘上会留一个永不下降、
速度冻结在 0 的『下载中 N』。没有通知是对的，但屏幕上有一处自相矛盾的常驻痕迹。

**主后果不变，也确实是 P1**：命中的行永久脱轨、集去重永久占位，没有任何在线路径能改回来。

另外两条标记重跑的后果不改数据，但一样难看：完结判定那条闩**只在有命中的那一轮才落**，
于是季末某一轮 ≥6 部同时完结时会被整批当成"首轮回填"而静默，一条通知都不发 ——
正是那段注释里点名要防的形状，被改名重新打开了。

### 修法：改键名必须带迁移

新增 `db.scoped_flag(key)` 与 `db.adopt_legacy_flag(key)`（与 `data_identity` 同住）：
读不到带身份的新键时先认领一次旧的全局键 —— **认到就把新键写下、把旧键删掉**。

删旧键这一步不能省：留着的话，以后切到另一个业务库时它会再被认领一次，
而那个库确实**从来没有**回填过，R26 想修的问题原样回来。

实现放在 `db` 而不是 `core/anime`，是因为三处标记里有一处在 `core/engine`，
而 engine 是 anime 的**下层**（anime import engine）—— 让它反过来 import anime 是层级倒置。

**端到端实测**：拿真库的只读快照起了一个自己的实例（端口 2399，`QB_ENABLED=false`），
启动日志逐字写着：

```
INFO 认领旧的一次性回填标记 _QB_PROGRESS_BACKFILLED → _QB_PROGRESS_BACKFILLED@sqlite:/…/real.db
     （存量安装升级，不再重跑那次回填）
```

守卫 `tests/test_legacy_flag_adoption.py` 六条，四条变异全部变红：
engine 不认领 / 认领后不删旧键 / 认领做成一律跳过 / 通知闩不认领。

## 一、在途闸漏了两条后台线，而现成的守卫**结构上看不见它们**

`engine.maintenance_blockers()` 逐条列出"跨 await 持业务库主键"的线，
R21 列了 2 条、R22 补到 5 条。这一轮的对抗审计找出**第 6、7 条**：

| 线 | 形状 |
|---|---|
| `archive_old_completed` | 读 `(id, info_hash)` 列表 → `await qb.delete()`（单次上限 45 秒）→ 出 await 后 `s.get(model_cls, tid)` 按主键写 `archived_at` |
| `sweep_finished` / `sweep_idle` | 读 `Anime.id` → `await notify_event()`（每条上限 `NOTIFY_TIMEOUT`）→ 回来 `s.get(Anime, a.id)` 写 `finished_at` |

而 `db/transfer.py` **保留主键**：两个库里 id=501 是两条毫不相干的记录。
维护窗口横在中间时，回写落进另一个库的另一行。

**为什么 R23 那条守卫抓不到**：它的判据是
「每一把模块级 `asyncio.Lock` 都必须被在途闸看见」—— 而这两条线**一把锁都没有**。
于是它们既不在闸里，也不在守卫的视野里：**约束的作用域比验证的作用域小**（第②种形状）。

修法就按闸自己那句注释办（"新增一条就往这儿加一行"）：
`worker._archive_lock` / `worker._sweep_lock` 两把锁，登记进闸，
R23 那条守卫从此自动覆盖它们，以后再加一条也一样。

同时把 `_maybe_archive` 的闭包与 `run_sweep` 的循环体各抽成模块级
`archive_round()` / `sweep_round()` —— **不是为了好看，是为了能测**：
用例要在**轮子内部**问一次闸，才测得到"这条线真的拿着锁跑"。
只断言"闸认识这把锁"的话，把 `async with` 整行删掉照样全绿（实测确认）。

三条变异全红：归档不持锁 / 巡检不持锁 / 闸里漏掉归档锁。

## 一之二、同一条 P1 还有**另一半**：换业务库时它照样重跑

旧键认领只发生一次，救不了这条路径：设置页『迁移数据』把含在下种子的库整个搬到 MySQL、
紧接着『切到 MySQL』→ `init_business_state` → 本函数。**新库没有它的身份标记**，
而新库里那些正在下载的行是从旧库原样搬过来的 —— 一把全写成 1.0。

**标记之外还要一道【数据本身】的判据。** 要回答的问题是「这个库里的 sent 行是不是
本功能上线**之前**留下的」，而那是关于数据的事实，不是关于标记的：
**上线前的库从来没写过 `qb_synced_at`**（那一列与 `qb_progress` 是同一批加的，
只有同步循环会写它）。所以库里只要存在任何一条 `qb_synced_at IS NOT NULL`，
就说明实时态跟踪在这个库上跑过 —— 此时的 `sent 且 progress<1` 是**真的在下**。

反向的漏判是安全方向：历史行留在 progress=0 上，会被同步循环当成在下的去查一次，
qB 查不到 → 现成的 `_QB_ABSENT` 那套把它收敛掉。

变异（去掉数据判据）当场变红。

## 一之三、alembic 跑 DDL 的连接**绕开了全部 MySQL 超时上界**（P1）

`db.make_mysql_engine` 给每个业务引擎装了 `connect_timeout=5` + `read/write_timeout=15`，
文档明写这是为了"主机连得上但库查不动"。但 `schema.upgrade()` 只用这个引擎读一次版本号，
**真正跑 DDL 的是 `alembic/env.py` 里 `engine_from_config(...)` 自己建的那个** ——
只有一个 URL，没有任何 `connect_args`。

后果不是"慢一点"：`schema.upgrade()` 的调用点全包在 `db.maintenance()` 里，
而 `finally` 要等它返回。对着一台**关机**的 MySQL 升级时，建连接挂到操作系统的 TCP 超时，
这期间 ① `get_session()` 对全站恒抛 `DatabaseBusy`（七个页面停在"数据库维护中"）；
② `db/schema.py` 的进程级 `_LOCK` 被那个线程占着 ⇒ 『切回本地 SQLite』这条**自救出口**
也拿不到锁；③ `busy_action` 的 `_BUSY['db-op']` 永不复位。**两个出口同时死，只能重启进程。**

修法：`db/schema._ddl_engine(engine)` —— MySQL 时用 `make_mysql_engine(url, query_timeout=False)`
另建一个交给 alembic（`cfg.attributes["connection"]`，`env.py` 本来就认这个键），用完即弃；
SQLite 直接用调用方的引擎。

**`query_timeout=False` 是有意的**：`read_timeout` 是每次 socket 读写的上界，
而一条 DDL（大表加索引）合法地跑几分钟很正常，套上它会把正常迁移拦腰切断 ——
那正是"表结构已经改了一半"最不能被打断的地方。这里要的只是**握手有上界**。

"DDL 被 MySQL 的元数据锁挡住"是另一件事（`lock_wait_timeout` 默认一年），
是个运维口径，记成 **E-50** 等你拍板。

**真 MySQL 上实测**（`10.0.10.20/autorss_audit_tmp`）：新库一路建到 `b7d2e4a91c66`、
复跑幂等、七张表与三个索引齐全，且 DDL 引擎确实是以 `query_timeout=False` 建的。
两条变异全红：不把引擎交给 alembic / DDL 引擎带上查询超时。

## 二、设置页还有一句在事件循环上同步碰 MySQL，而 E-36 的守卫对它是空的

`_switch_backend` 里 `db.switch_data_engine` 老老实实走了 `await run.io_bound(...)`，
紧接着的 `worker.init_business_state(...)` 是**裸的同步调用** —— 而此刻 `db.engine`
已经指向 MySQL。它做的全是同步库往返：`seed_source_groups()`、
`backfill_legacy_progress_once()`（对两张种子表各一次全表扫 + 逐行 UPDATE + commit）。

真库规模实测 78ms；但 `sent` 是只增不减的终态、行数随挂机线性长，
而业务引擎带 `read_timeout=15` + `connect_timeout=5` ——
刚切过去的 MySQL 立刻变慢时，最坏能把整站冻几十秒。

**守卫为什么没报**：`test_the_settings_page_never_touches_mysql_on_the_event_loop`
的判据是「整棵 AST 子树里出现过 `io_bound`」。`_switch_backend` 因为前一句恒满足，
**同一个处理器里其余的同步库调用永远报不出来**。

判据改成**逐个调用点**，并保留原来的子树级判据当兜底，再加第三半：

> 处理器里的**内层同步小函数**（`_ping` / `_probe` 这类，身体里真的碰库的）
> 不许被直接调用 —— 它们存在的唯一理由就是被 `io_bound` 拎到线程里去。

第三半是必须的：把 `await run.io_bound(_ping)` 改成 `_ping()`，
前两半**都是绿的**（名字不在名单里；处理器里别处仍有 `io_bound`）。实测确认。

收紧的过程中还出过一次**我自己的假阳性**：第一版把 `make_mysql_engine` 也列进
"必须上线程"的名单，于是把 `_migrate` 里正确的写法报成了违规 ——
`create_engine` 是**惰性**的、不建连接（所以那里才另外写了个 `_ping()` 去真连一次）。
它是"这个处理器碰 MySQL"的**标记**，不是违规本身。

## 三、我自己 R26 加的检测是个 N+1，挂在仪表盘的同步路径上

`suspect_wrong_binding()` 逐部番各查一次种子表（判据里一次、取明细再一次），
而它挂在 `overview_head` 上 —— 每次渲染 + 每 30 秒的定时刷新各跑一遍，
且是**同步函数、跑在事件循环上**。

真库快照实测：

| | 改前 | 改后 |
|---|---|---|
| `suspect_wrong_binding()` | **120.5 ms** | **26.4 ms** |
| 同页 `overview()` 对照 | 33.7 ms | 33.7 ms |

判据只用到 `episode` / `release_time` 两列，所以改成一条**列投影**查询全量取回、
在内存里按 `anime_id` 分组。19k 条种子的库上，这个差别是"几万个 ORM 实体"与"几万个元组"。

判据本体抽成 `_binding_looks_wrong_rows(a, rows)`，`binding_looks_wrong(s, a)` 取行后委托它 ——
**判据只有一份实现**，两个调用形态都指向它。

结果逐字不变（真库上仍然只命中 anime#6 的 24 条，集号 1~8）。
守卫数的是**真正发到数据库的语句条数**：番数 3 → 30，语句数必须一条不涨。
变异（退回 N+1）从 2 条涨到 60+ 条，当场变红。

## 七、留给你拍板的（新增 2 条，共 15 条）

**E-49 崩溃后复位『交付中』残骸时，怎么知道它重下之前是什么状态**（详见 `DECISIONS.md`）。

详情页对 `deleted/excluded/stalled/已归档` 都显示『下载』按钮。点它进锁段会把
`status` 置 `downloading`、`archived_at` 清空并 commit，然后才去 `await` 取种（最长 180 秒）。
协程还活着时 `_keep_orig` 会整组放回；**协程活不到那一步时**
（进程被杀 / 回写撞库抖动），`sweep_stale_delivering` 把它**无条件写成 pending**。

最重的是原状态 `stalled`：丢掉 HAVE 身份而半成品文件还在 `save_path`，
flush 当场为同一集挑另一个源下第二份到**同一个目录**。

两个选项都不该由我替你选：A 要开一条 revision 加列（动你的库 schema），
B 不动 schema 但改的是一条写着"原子占位"的核心不变量（本项目单进程时等价，
上多副本会静默失效）。选定之后我会连守卫一起补。
